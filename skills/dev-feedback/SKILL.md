# Dev Feedback

Оценка работы разработчика за период, где каждое утверждение подкреплено МР, цитатой из диффа или треда.

## Подготовка

Нужны `glab` (авторизован на инстансе) и Python 3.9+.

Субагенты вызывают скрипты через Bash и без разрешения встанут на approve-промпте. Перед первым запуском предложи добавить в **user-level** `~/.claude/settings.json` (project-local субагенты не читают) оба пути — симлинк и реальный:

```json
{ "permissions": { "allow": [
  "Bash(python3 /Users/<you>/.claude/skills/dev-feedback/scripts/*)",
  "Bash(python3 /ABSOLUTE/REPO/PATH/skills/dev-feedback/scripts/*)"
] } }
```

`SKILL_DIR` — путь из строки `Base directory for this skill: …`. Нет её — первый существующий из `~/.claude/skills/dev-feedback` и пути в репозитории. Скрипты от cwd не зависят.

## Step 1: Входные данные

Возьми из аргументов, недостающее спроси:

1. username в GitLab;
2. hostname инстанса;
3. период: `--months N` (по умолчанию 3) или `--since YYYY-MM-DD`;
4. часовой пояс команды от UTC, если не Москва (для рабочих часов);
5. какие стадии между аппрувом и отгрузкой не оставляют следа в GitLab (например, тестирование отдельной командой);
6. контекст (опционально): что пользователь уже знает, на что смотреть.

Всё спрашивай одним сообщением — дальше прогон идёт без остановок.

## Step 2: Сбор МР

```bash
python3 "SKILL_DIR/scripts/fetch_mrs.py" --username U --hostname H --months N > /tmp/dev-feedback-mrs.json
```

Файл целиком в контекст не читай — сводку собери `jq` по `.summary`. Имя для заголовка отчёта: `glab api users?username=U --hostname H | jq -r '.[0].name'` (GitLab отдаёт латиницей — в отчёте пиши по-русски: «Иван Иванов»).

Окно — по активности: МР попадает, если внутри периода он создан, смержен, закрыт или получил коммит разработчика либо человеческую ноту. Поэтому в отчёт входит и МР, начатый до периода, а открытый МР без движения — нет. Причины попадания — в `activity_reasons`. Собираются все три состояния (`--states merged,closed,opened`).

Категории: `authored` (автор и assignee), `author_only` (автор с коммитами, не assignee), `assignee_only`.

`summary.multi_mr_tasks` — МР, сгруппированные по ключу тикета в ветке (`hotfix/TASK-944`, `hotfix/TASK-944-2` → `TASK-944`). Группа — одна задача с несколькими подходами, считай её одной задачей и отмечай факт переделок.

Покажи пользователю сводку:

```
Найдено N МР в M проектах за FROM → TO (по активности)
- merged M / closed C / opened O; отсечено без активности S
- активность: создан N / смержен N / закрыт N / обсуждение N / коммиты N
- authored X / author_only Y / assignee_only Z
- проекты: …
- несколько МР на задачу: TASK-944 → !28330 (closed), !28335 (merged)
```

0 МР — остановись и сообщи.

## Step 2б: Метрики скорости

Цифры по таймстампам считает только скрипт.

```bash
python3 "SKILL_DIR/scripts/fetch_timing.py" --username U --hostname H \
  --mrs-json /tmp/dev-feedback-mrs.json --tz-offset 3 > /tmp/dev-feedback-timing.json
```

`--tz-offset` — зона команды из Step 1 (3 = MSK). `--identity` (повторяемый) — дополнительная подпись коммитов, если разработчик коммитит под другим именем или почтой. ~2 минуты на 60 МР.

Читай `.totals` и `.warnings`; из `.per_mr` доставай точечно через `jq` под конкретный пример.

Что в `.totals`:

- `lead_time_h` — создание → merge;
- `lead_split_h` — три отрезка: создание → аппрув (последний «аудит ок» до метки) → взятие в отгрузку (нота `.` от `deployer`) → merge;
- `deploy_outcome` — что было после метки `.`: ничего — чисто, только коммиты — конфликт, коммиты и комментарии — доработки;
- `reaction_h` — замечание ревьюера → следующий не-мерж коммит разработчика;
- `waves` — порции правок после порций замечаний;
- `comments` — содержательные замечания на МР (апрувы вынесены в `approvals_count`);
- `closed`, `open` — закрытые и оставшиеся в работе.

Как читать:

- **Разработчику принадлежит только `reaction_h`.** Ожидание аппрува, поезда и тестирования — процесс. Отрезок между аппрувом и меткой объясняй через стадии без следа из Step 1. Кучный `deploy_mark_hour_hist` (всё в 10–12) — поезд по расписанию.
- **Выводы строй на `work_median`** (пн–пт 10–19 в зоне `--tz-offset`); календарные часы — контекст. `work_share_pct` ниже ~40 % — календарная медиана говорит о графике, а не о скорости.
- **Доли отрезков — по суммам и только на МР с полной цепочкой** (`mrs_with_full_chain`). Метки `.` нет ни у одного МР — разрез неприменим, оставайся на общем lead time.
- **Волны:** 1 — нормальный цикл. Сигнал — устойчивые 3+ или 0 при ненулевых комментариях (отвечает словами, а не кодом — проверь `.reactions[].fixed`).
- **`n_without_fix`** — это аргументированный отказ или игнор; различает только текст ответа в `.per_mr[].reactions`.
- **Авторство коммитов** сверяется по подстроке имени. Проверь `commit_signatures`: тревога — если среди трёх крупнейших чужих подписей видна его вторая почта или в `warnings` «ни один коммит не сопоставлен» (тогда волны и реакция по МР — нули; перезапусти с `--identity`). Rebase-предупреждения в `warnings` тоже делают волны и реакцию по МР недостоверными.
- **Открытые:** `approved_waiting` ждёт отгрузки — вопросов к разработчику нет; вопрос — к `with_unanswered_comments`. `drafts` отдельно.
- **Закрытые** до вывода о переделке проверь: `to_release_branch` (ветки `build_*` закрывают штатно), пачка в `close_date_hist` (плановая чистка), warning «закрыт, хотя был взят в отгрузку» (правка уехала другим МР). Про оставшиеся сначала спроси, что было с задачей. Много `approved_before_close` — вопрос к постановке задач.

Покажи пользователю сводку цифрами.

## Step 3: Батчи субагентов

`batch = max(5, ceil(N / 10))`, не больше 10 субагентов, все параллельно в одном сообщении, **`model: "haiku"` в каждом вызове** — диффы самая тяжёлая часть контекста, а работа батча механическая. Перезапуск — только при механическом сбое (невалидный JSON, скрипт упал на всём батче), один раз и тоже на `haiku`.

Промпт (подставь значения; `{skill_dir}` — абсолютный `SKILL_DIR`):

---

Ты разбираешь МР разработчика **{username}**. Для каждого МР из списка запусти:

```bash
python3 "{skill_dir}/scripts/fetch_mr_details.py" --project-id {project_id} --mr-iid {mr_iid} --hostname {hostname}
```

МР: {batch_json — project_id, iid, title, category, state}

`closed` — не доехал до мастера, `opened` — не закончен; помечай их и результат им не приписывай. Незакрытые замечания и отсутствие тестов у открытого МР — норма процесса. МР с одним ключом тикета в ветке — подходы к одной задаче.

Для каждого МР:

1. `task_type`: фича / багфикс / рефакторинг / техдолг / хотфикс / i18n / инфра.
2. `complexity`: простая (1–3 файла) / средняя (4–15, нетривиальная логика) / сложная (15+ или архитектура).
3. `modules`: затронутые части системы.
4. `code_quality`: дублирование, абстракции, именование, ошибки и edge cases, паттерны — в коде **этого** МР. **Каждый пункт — файл и дословная цитата строки из диффа**, не из комментария ревьюера; процитировать нечего — пустой список.
5. `review_dynamics`: кто что заметил, как разработчик отреагировал (принял / аргументировал / проигнорировал), повторяющиеся замечания. Каждый пункт `notable_comments` — с дословной цитатой из треда. Считать комментарии не нужно.
6. `summary`: одно предложение — что делает МР.
7. `notable`: одна вещь, которую пункты выше не ловят (неочевидное решение, компромисс, находка в треде), с дословной цитатой из диффа или треда; ничего — `null`.

Ошибка скрипта на МР — отметь и продолжай. Верни JSON-массив:

```json
[{
  "project_id": 42, "iid": 123, "project_name": "service/core", "title": "...",
  "summary": "Добавил обработку нового типа ошибки в API бронирования",
  "category": "authored", "state": "merged", "task_type": "bugfix",
  "complexity": "средняя", "modules": ["api"],
  "code_quality": {
    "positives": [{"claim": "вынес общий предикат вместо двух копий",
                   "file": "src/entities/todo/model/isActive.ts",
                   "quote": "export const isActive = (todo: Todo) =>"}],
    "issues": []
  },
  "review_dynamics": {
    "notable_comments": [{"text": "ревьюер указал на отсутствие теста — разработчик добавил",
                          "quote": "а тест на пустой список?"}],
    "recurring_issues": []},
  "notable": null
}]
```

## Step 3б: Глубокое чтение 2–3 МР

Чек-лист батча даёт однотипный материал; суть МР («не замена констант, а смена модели тарифов») видит только основная модель.

Кандидаты: merged или opened, `authored`/`author_only`, `complexity: сложная`, по убыванию `comments_count` из `.per_mr`; группа `multi_mr_tasks` — один кандидат. На каждый из 2–3 — субагент **без `model`**, все параллельно. Промпт:

> Прочитай МР {project_id}!{iid} разработчика {username}:
> `python3 "{skill_dir}/scripts/fetch_mr_details.py" --project-id {project_id} --mr-iid {iid} --hostname {hostname}`.
> Ответь 1–3 предложениями на каждый вопрос, с якорем (файл + дословная цитата из диффа или дословная цитата из треда):
> 1. Что МР меняет по сути: какая модель, контракт или поведение было и стало.
> 2. Какое неочевидное решение или компромисс принял разработчик и чем обосновал.
> 3. Как он думает по треду: где спорил и чем, где уступил, что упустил, что нашёл сам.
> Нечего сказать — `null`. Верни `{"project_id", "iid", "essence", "decision", "thinking"}`, каждое поле `{"text", "file", "quote"}` или `null`.

## Step 4: Синтез

**Гейт.** Сложи ответы Step 3 и 3б в один JSON-массив и прогони:

```bash
python3 "SKILL_DIR/scripts/check_quotes.py" --results /tmp/dev-feedback-results.json --out /tmp/dev-feedback-gated.json
```

Скрипт сверяет каждую цитату с кэшем `fetch_mr_details.py` (`/tmp/dev-feedback/<project_id>-<iid>.json`): `code_quality` и `essence` — только с диффом, `notable_comments` и `thinking` — только с тредами, `notable` и `decision` — с любым. Синтез строй на `-gated.json`. Выброшенное не добирай перезапуском: у него не было опоры и до гейта. Число «осталось N из M» из вывода скрипта передай пользователю; хочет глубже — предложи прогнать через Step 3б ещё 3–5 МР.

Числа (комментарии на МР, реакция, волны) бери только из `/tmp/dev-feedback-timing.json`: батчи их считают неверно.

**Тезис.** Сформулируй для себя 2–3 фразы: что отличает этого разработчика за период — «свой код продуман, периметр вокруг хуже», «поздние раунды ревью находят новые дефекты, а не доделки». Бери их из `notable`, Step 3б, повторяющихся замечаний и контекста пользователя. Колонка строится вокруг тезиса, порядок абзацев задаёт аргумент.

**Что должно прозвучать** (полнота, не порядок):

- 2–4 темы работы по смыслу, не по МР;
- самостоятельность по сложности — фраза с примером;
- реакция на ревью — как спорит и как уступает, с цитатами из тредов;
- скорость — `reaction_h` и одной фразой, куда уходит остальное время;
- что в работе — только МР, к которым есть вопрос; ждущие поезда — одной фразой;
- 1–3 повторяющихся зоны роста со ссылками на МР, каждая с действием;
- сильная сторона в коде из пунктов после гейта.

Пункту нечего сказать — одна фраза или ничего.

**Форма — колонка в деловой газете.** Заголовок — имя; первая строка — период и объём; первый абзац — лид с главной темой и тезисом. Сплошной текст без таблиц и подзаголовков; один список допустим для действий в зонах роста. 400–700 слов. От первого лица тимлида, о разработчике — по имени. Каждое утверждение опирается на МР или цитату; о коде — только пункты после гейта. Цифры — только те, что держат вывод, и с объяснённым остатком: «22 из 23 прошли чисто, одна — с конфликтом».

**Вычитка до показа.** По каждому предложению: есть ли в нём факт или вывод, которого нет в соседнем? Нет — удали; два об одном — оставь сильное. Вычеркни оценки без факта («качественный код», «хорошо справляется»), канцелярит («стоит отметить», «в целом», «является», «демонстрирует», «не только… но и»), пересказ заголовков МР, повтор цифр, финал, повторяющий лид. Пользователь видит только вычитанную версию.

**Служебное** — гейт, сбои сети, правки скриптов, сомнения в данных — отдельным блоком в чате после колонки; внутри колонки — максимум строка «Данные: …» в конце.

Вывод — в чате, файлов не создавай.

## Ограничения

- Только GitLab: трекер задач недоступен.
- Диффы обрезаются до 500 строк на файл.
- Чужая нота на старом МР втягивает его в окно.
- `multi_mr_tasks` вырождается, если ветки не называют по тикету.
- lead time МР, начатого до периода, включает часы вне окна.
- Праздники и отпуска в рабочих часах не учитываются.
- Разрез lead time держится на конвенциях «аудит ок» и ноты `.`.
