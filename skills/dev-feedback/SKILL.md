# Dev Feedback

Ты формируешь обратную связь на разработчика, анализируя его merge requests в GitLab.
Цель — дать объективную, подкреплённую примерами из кода оценку работы за период.

## Prerequisites

- `glab` CLI установлен и авторизован на целевом GitLab-инстансе
- Python 3.9+

### Permissions для субагентов

Скилл запускает субагентов, которым нужен доступ к Bash для вызова скриптов.
Без разрешений субагенты не смогут работать автономно и скилл упадёт на Step 3.

Перед первым запуском предложи пользователю добавить в `~/.claude/settings.json`
(именно **user-level** — субагенты не подхватывают project-local `settings.local.json`):

```json
{
  "permissions": {
    "allow": [
      "Bash(python3 /Users/<you>/.claude/skills/dev-feedback/scripts/*)",
      "Bash(python3 /ABSOLUTE/REPO/PATH/skills/dev-feedback/scripts/*)"
    ]
  }
}
```

Путь бери из `Base directory for this skill: <путь>` (см. Step 2), а не угадывай.
Скилл обычно установлен через симлинк, поэтому добавь **оба** пути — симлинк
(`~/.claude/skills/dev-feedback`) и реальный путь в репозитории, — иначе субагент
упрётся в approve-промпт на Step 3.

## Workflow

### Step 1: Входные данные

Спроси у пользователя (если не передано в аргументах):

1. **Username** разработчика в GitLab (например, `kkurentsov`)
2. **Hostname** GitLab-инстанса (например, `git.example.com`)
3. **Период** — количество месяцев (по умолчанию 3). Варианты: 1, 2, 3, 6
4. **Контекст** (опционально) — что пользователь уже знает о разработчике, на что обратить особое внимание, какие аспекты важнее

### Step 2: Сбор МР-ов

Запусти скрипт сбора:

```bash
python3 "SKILL_DIR/scripts/fetch_mrs.py" \
  --username USERNAME \
  --months MONTHS \
  --hostname HOSTNAME > /tmp/dev-feedback-mrs.json
```

Сохраняй вывод в файл — он нужен на Step 2б. В контекст целиком не читай:
сводку ниже собери через `jq` по `.summary`.

Где `SKILL_DIR` — абсолютный путь к директории этого скилла. Бери его из строки `Base directory for this skill: <путь>`, которую харнесс печатает при загрузке скилла (НЕ угадывай и не используй `dirname`/cwd). Если `Base directory` недоступен — возьми первый существующий: `~/.claude/skills/dev-feedback` (симлинк) или реальный путь в репозитории. Скрипты читают/пишут по абсолютным путям и от cwd не зависят.

**Окно — по активности, а не по дате создания.** В отчёт попадает МР, у которого
внутри периода произошло хоть что-то: создан, смержен, закрыт, есть коммит
разработчика или человеческая нота. МР, пролежавший весь период без движения, не
попадает ни в каком состоянии — даже открытый, даже свой. На проверочной выборке
это отсекло 14 открытых МР-ов возрастом до года.

Обратное тоже важно: МР, заведённый **до** периода и доделанный внутри него — работа
этого периода. Предфильтр идёт по `updated_after`, и на месячном окне это дало 43
merged вместо 27 по `created_after` — 16 МР были бы потеряны.

Собираются **все три состояния** (`--states merged,closed,opened`):

| состояние | зачем | сколько на проверочной выборке (3 мес) |
|---|---|---|
| merged | отгруженная работа | 118 |
| closed | работа, не доехавшая до мастера | 13, из них у всех был «аудит ок» |
| opened | что осталось в работе на конец периода | 25, из них 8 ждут поезда после аппрува |

Верхняя граница окна на стороне API не задаётся намеренно: иначе МР, тронутый уже
после периода, выпал бы из отчёта за прошлый период. Обе границы проверяются локально.

Скрипт выведет JSON с тремя категориями МР-ов:
- **authored** — разработчик автор И assignee
- **author_only** — разработчик автор, но НЕ assignee (проверено наличие коммитов)
- **assignee_only** — разработчик НЕ автор, но assignee

Покажи пользователю сводку:

```
Найдено N МР-ов в M проектах за период FROM → TO (по активности в окне)
- merged: M, closed: C, opened: O
- отсечено без активности в окне: S
- активность засчитана по: создан N / смержен N / закрыт N / обсуждение N / коммиты N
- authored: X
- author_only: Y
- assignee_only: Z
- проекты: list
- несколько МР на одну задачу: TASK-944 → !28330 (closed), !28331 (closed), !28335 (merged), !28336 (closed)
```

`summary.multi_mr_tasks` группирует МР-ы по ключу тикета из имени ветки
(`hotfix/TASK-944` и `hotfix/TASK-944-2` → одна группа `TASK-944`). Это входные
данные для Step 4: такая группа — **одна** задача с несколькими подходами, а не
четыре задачи. Считать их отдельными — завысить объём работы и потерять сам факт
переделок.

Если МР-ов 0 — останови работу, сообщи пользователю.

### Step 2б: Скорость реакции (метрики)

Считает скрипт, не субагент и не ты: цифры по таймстампам LLM считать нельзя.

```bash
python3 "SKILL_DIR/scripts/fetch_timing.py" \
  --username USERNAME \
  --hostname HOSTNAME \
  --mrs-json /tmp/dev-feedback-mrs.json \
  --tz-offset 3 > /tmp/dev-feedback-timing.json
```

`--tz-offset` — смещение рабочей зоны команды от UTC (по умолчанию 3 = MSK).
Спроси, если команда не в Москве: от него зависят рабочие часы.

Скрипт делает 2 запроса на МР (notes + commits), на 60 МР это ~2 минуты.
В контекст читай только `.totals` и `.warnings` — `.per_mr` большой, из него
доставай точечно (`jq '.per_mr[] | select(.waves > 3)'`) под конкретный пример.

**Что считается:**

| метрика | как | где смотреть |
|---|---|---|
| lead time | `created_at` → `merged_at`, медиана | `.totals.lead_time_h` |
| разрез lead time | три отрезка: создание → аппрув → взятие в отгрузку → merge | `.totals.lead_split_h` |
| исход отгрузки | что было после метки: чисто / конфликт / доработки | `.totals.deploy_outcome` |
| время на замечание | от комментария ревьюера до первого следующего коммита разработчика | `.totals.reaction_h` |
| волны правок | серия коммитов после очередной порции замечаний; 0 = замечаний не было или на них не отвечали кодом | `.totals.waves` |
| комментариев на МР | среднее и медиана содержательных замечаний | `.totals.comments` |
| закрытые МР | сколько, доходили ли до аппрува, сколько в них коммитов | `.totals.closed` |
| открытые МР | что осталось в работе, возраст, сколько ждёт поезда | `.totals.open` |

**Разрез lead time — три отрезка, не два:**

| отрезок | веха | что означает |
|---|---|---|
| создание → аппрув | последний «аудит ок» до метки отгрузки | пропускная способность ревью |
| аппрув → взятие в отгрузку | нота с телом ровно `.` (автор `deployer`) | расписание поезда, тестирование, очередь |
| взятие в отгрузку → merge | метка → `merged_at` | сама отгрузка |

Без разреза «332 ч до merge» читается как «медленно мержат», хотя половина пути —
ожидание аппрува. Аппрув берётся **последний до метки**: у МР с доработками их
несколько, и операционный тот, после которого МР поехал.

Исход отгрузки читается по тому, что произошло **после** метки `.`: ничего —
чисто, только коммиты — конфликт при отгрузке, коммиты и комментарии —
требовались доработки. Устойчивая доля «доработок» — сигнал о качестве, а не о
скорости.

**Как читать — иначе выводы будут неверными:**

- **Отрезки принадлежат разным людям.** Разработчику принадлежит только реакция
  на замечания внутри первого отрезка. Ожидание аппрува и поезда — процесс, в
  фидбэк как его характеристику не пиши.
- **Слепая зона во втором отрезке.** Между аппрувом и взятием в отгрузку может
  лежать работа без следа в GitLab — например тестирование отдельной командой.
  Спроси, какие стадии процесса не оставляют следа, прежде чем объяснять этот
  отрезок; иначе получится уверенный вывод про то, чего в данных нет.
- **Час метки говорит, ручное это решение или расписание.** Кучный
  `deploy_mark_hour_hist` (всё в 10–12) означает поезд по расписанию — второй
  отрезок тогда про ожидание, а не про кого-то конкретного.
- **Доли считаются по суммам и только на МР с полной цепочкой** — смотри
  `mrs_with_full_chain`. Если метка `.` в этом инстансе не используется вообще
  (`mrs_without_deploy_mark` = все), разрез неприменим: скажи это прямо и
  оставайся на общем lead time.

- **Календарные часы без рабочих не выноси.** `calendar_median` включает ночи и
  выходные и завышает картину в 2–3 раза: МР, созданный в четверг вечером и
  прочитанный в понедельник, к скорости отношения не имеет. Основной вывод строй
  на `work_median` (пн–пт 10:00–19:00), календарные — как контекст. Если
  `work_share_pct` ниже ~40 %, календарная медиана говорит о графике работы, а не
  о скорости.
- **Апрувы не считаются замечаниями.** «ок», «аудит ок», «кросс-аудит ок»
  отфильтрованы в `approvals_count`; попади они в знаменатель — среднее число
  комментариев раздуется, а доля каждой темы занизится.
- **Волны — это не «сколько раз ошибся».** 1 волна на МР — нормальный цикл
  ревью. Сигнал — устойчивые 3+ (замечания приходят порциями, потому что
  предыдущая правка их не закрыла) или 0 при ненулевых `comments_count`
  (на замечания отвечают словами, а не кодом — проверь по `.reactions[].fixed`).
- **Мерж мастера в ветку реакцией не считается.** Для времени на замечание и волн
  берутся только не-мерж коммиты (`commits_fix`), для исхода отгрузки — все
  (`commits_mine`): мерж после метки `.` и есть признак конфликта. Без этого
  разреза на проверочной выборке 30 из 30 замечаний выглядели «закрытыми правкой»,
  хотя два из них закрыл мерж мастера, а тред кончился «в целом ладно, не критично».
- **Опознание автора коммитов проверь глазами.** Почту чужого юзера GitLab не
  отдаёт, поэтому коммиты сопоставляются по подстроке username/имени в
  `author_name`/`author_email`. Посмотри `commit_signatures`: там все опознанные
  подписи и три крупнейшие чужие. Чужих всегда много (в коммитах МР лежит весь
  влитый мастер — на выборке 535 своих против 700+ чужих в 36 подписях), поэтому
  сам по себе `matched: false` ничего не значит. Тревога — если среди трёх чужих
  видна подпись самого разработчика со второй почтой, либо если в `warnings` есть
  «ни один коммит не сопоставлен».
- **`n_without_fix` читай вместе с содержанием.** Замечание без последующего
  коммита — это либо аргументированный отказ (хорошо), либо игнор (плохо).
  Различает только текст: возьми такие ноты из `.per_mr[].reactions` и посмотри,
  что разработчик ответил.
- **Открытые МР — это незавершённая работа, а не провал.** `approved_waiting` —
  заапрувлено и ждёт отгрузки (работа сделана, к разработчику вопросов нет);
  `with_unanswered_comments` — висят замечания без правки, вот это к нему;
  `age_work_max` — самый старый МР в работе. `drafts` считай отдельно: черновик
  никто и не обязан был ревьюить.
- **Закрытые и открытые МР в lead time и вехи отгрузки не входят** — у них нет `merged_at`.
  Они считаются в комментариях, реакции и волнах (ревью-то они получали) и
  отдельно живут в `.totals.closed`. Разделение состояний видно в `mrs` / `mrs_merged`.
- **Закрытый МР — не синоним брошенной работы, проверь три вещи перед выводом.**
  `to_release_branch` — МР в ветку `build_*` закрывают штатно, это часть процесса
  отгрузки. `close_date_hist` — пачка закрытий в один день (на проверочной выборке
  4 + 4) означает плановую чистку, а не провал. `warnings` — «закрыт, хотя был
  взят в отгрузку» означает, что правка уехала другим МР. И только оставшееся
  обсуждай как переделку, да и то сначала спроси, что было с задачей.
- **`approved_before_close` — самый содержательный из этих счётчиков.** Работа,
  доведённая до «аудит ок» и закрытая, стоила и разработчику, и ревьюеру. Если
  таких много — вопрос не к разработчику, а к тому, как ставятся задачи.
- **Слепая зона: между аппрувом и мержем может лежать работа без следа в GitLab**
  (тестирование, расписание отгрузки, очередь). Приписывать этот отрезок
  разработчику нельзя. Если lead time большой, а `reaction_h` маленький — узкое
  место не в нём; так и скажи.
- **`warnings` не игнорируй.** «ни один коммит не сопоставлен» означает, что
  разработчик коммитит под другим именем/почтой: волны и время реакции по этому
  МР — нули, и в выводы их брать нельзя.
- Медианы отрезков не складываются в медиану целого — доли считай по суммам.

Покажи пользователю компактную сводку цифрами, затем переходи к Step 3.

### Step 3: Анализ через субагентов

Размер батча подбирай так, чтобы субагентов вышло **не больше 10**:
`batch = max(5, ceil(N / 10))`. Окно по активности даёт заметно больше МР-ов, чем
раньше (на проверочной выборке 156 за 3 месяца) — фиксированный батч по 5 превратился
бы в 32 субагента. Все субагенты запускаются **параллельно в одном сообщении**
через Agent tool.

**Модель субагента — `model: "haiku"`, отдельным параметром в каждом вызове `Agent`.**
Работа батча в основном механическая: прогнать скрипт, разметить тип и сложность по
числу файлов, выписать модули и пересказать треды. Без параметра батч наследует
основную модель, а диффы — самая жирная часть контекста во всём скилле (500 строк на
файл × десятки файлов × 156 МР). Синтез в Step 4 остаётся на основной модели: он
судит период целиком.

**Перезапуск батча — только при механическом сбое** (ответ не разобрался как JSON,
скрипт упал на всех МР батча), и **на той же `haiku`**, один раз. Пункты без якоря
перезапуска не требуют: гейт в Step 4 их выбросит, а второй проход на основной модели
оплатил бы оба прохода ради материала, которого в первом и не было. Батч, вернувший
пустой `issues` с якорями в `positives`, отработал правильно.

Промпт для каждого субагента (подставь реальные значения; `{skill_dir}` — тот же абсолютный `SKILL_DIR` из Step 2, субагенту cwd неизвестен):

---

**НАЧАЛО ПРОМПТА СУБАГЕНТА**

Ты анализируешь merge requests разработчика **{username}** для формирования обратной связи.
Для каждого МР из списка ниже запусти скрипт и проанализируй результат.

**Скрипт для получения данных МР:**
```bash
python3 "{skill_dir}/scripts/fetch_mr_details.py" \
  --project-id {project_id} \
  --mr-iid {mr_iid} \
  --hostname {hostname}
```

**Список МР-ов для анализа:**
{batch_json — массив объектов с project_id, iid, title, category}

**Состояние МР** приходит в `state`. Закрытый (`closed`) — работа, не доехавшая до
мастера; открытый (`opened`) — работа, ещё не законченная на конец периода. Оба
анализируй наравне с остальными, но в выводе помечай отдельно и не приписывай им
результат. У открытого МР незакрытые замечания и отсутствие тестов — нормальное
состояние процесса, а не дефект: в зоны роста их не выноси. Если несколько МР идут по одной задаче (совпадает ключ
тикета в ветке) — это подходы к одной задаче, а не разные задачи.

**Для каждого МР определи:**

1. **Тип задачи**: фича / багфикс / рефакторинг / техдолг / хотфикс / i18n / инфра
2. **Сложность**: простая (1-3 файла, тривиальные изменения) / средняя (4-15 файлов, нетривиальная логика) / сложная (15+ файлов или архитектурные изменения)
3. **Модули и сервисы**: какие части системы затронуты
4. **Качество кода** (по диффу). **Каждый пункт — с якорем: путь к файлу и дословная
   цитата строки из диффа.** Утверждение без якоря не пиши вообще: «хорошая
   декомпозиция» или «местами дублирование» без файла и строки — это шум, который
   на этапе синтеза всё равно будет выброшен. Нечего процитировать — оставь список пустым.
   - Дублирование кода
   - Уровень абстракций (есть ли переиспользуемые решения или всё инлайново)
   - Именование переменных и функций
   - Обработка ошибок и edge cases
   - Паттерны (или антипаттерны)
5. **Ревью-динамика** (по комментариям):
   - Какие замечания оставлены (и кем)
   - Как разработчик реагировал — принял, аргументировал, проигнорировал
   - Есть ли повторяющиеся замечания (одна и та же ошибка в разных МР)
6. **Краткое описание**: одно предложение — что делает МР

**Верни результат как JSON-массив:**
```json
[
  {
    "iid": 123,
    "project_name": "service/core",
```

### Step 4: Синтез фидбэка

Когда все субагенты вернут результаты, собери их и сформируй текст обратной связи.

**Сначала гейт, потом синтез.** Пройди по всем `code_quality` и выброси пункт, у
которого пустой `file` или пустой `quote`, либо цитата не встречается в диффе этого
МР. Это дёшево проверить и это единственная защита от того, что удешевлённая модель
батча вернёт правдоподобные общие слова вместо наблюдений.

Выброшенное **не добирай перезапуском** — ни на основной модели, ни на `haiku`.
Пункт без якоря нечем подтвердить, значит в фидбэк он не годился и до гейта;
перезапуск оплатил бы два прохода ради нового материала, а не ради потерянного.
Остальная часть ответа батча (тип, сложность, модули, ревью-динамика, описание)
механическая и гейтом не затрагивается — она остаётся в работе целиком.

Посчитай выброшенное и **назови число пользователю**: «после гейта осталось N
наблюдений о коде из M». Мало — так и скажи в отчёте, что материал тонкий, вместо
того чтобы добирать общими словами. Если пользователь хочет глубже по коду, это его
решение о деньгах: предложи прогнать **точечно 3–5 самых крупных МР** на основной
модели, а не перезапускать батчи. Оставшиеся после гейта пункты — и есть материал
для «зон роста»; ничего сверх них не додумывай.

**Структура фидбэка:**

```markdown
# {Имя Фамилия разработчика}

Если смотреть по мр-ам, то работал(а) над такими задачами:
- {группировка по тематике, не по МР-ам — объединяй связанные МР-ы в одну задачу;
  группы из `summary.multi_mr_tasks` — это одна задача с несколькими подходами}
- {описывай суть, а не заголовки МР-ов}

{Какие сервисы/проекты затронул(а). Отметь, если работал(а) в нескольких — это плюс.
Упомяни если осваивал(а) новые инструменты, библиотеки, подходы.}

{Оценка самостоятельности:
- Простые задачи — полностью самостоятелен?
- Средней сложности — автономен или требует помощь?
- Сложные — обращается за помощью при затруднениях?
Основывайся на сложности МР-ов и характере ревью-комментариев.}

{Реакция на замечания в ревью:
- Адекватно реагирует?
- Учится — не повторяет одни и те же ошибки?
- Аргументирует свою позицию конструктивно?
Приведи конкретные примеры из комментариев.}

**Скорость и цикл ревью** (цифры из Step 2б, все — медианы за период):

| | значение |
|---|---|
| МР открыт → смержен | X рабочих ч (Y календарных) |
| из них: создание → аппрув | X рабочих ч (N % пути) |
| аппрув → взятие в отгрузку | X рабочих ч (N %) |
| взятие в отгрузку → merge | X рабочих ч (N %) |
| исход отгрузки | чисто N / конфликт N / доработки N |
| закрытых МР | N из M, из них с аппрувом N |
| открыто на конец периода | N, из них ждут отгрузки N, с висящими замечаниями N |
| замечание → правка | X рабочих ч, N из M замечаний закрыты коммитом |
| волн правок на МР | X (максимум Y) |
| замечаний на МР | X в среднем, Z МР без единого замечания |

{Интерпретация в 3–5 предложениях: быстро ли подхватывает замечания, стабилен ли
цикл, что за выбросы. Каждый вывод — со ссылкой на конкретный МР из `.per_mr`.
Не приписывай разработчику отрезки, где он не действует — см. слепую зону в Step 2б.}

{Что осталось в работе на конец периода — из `.totals.open`: сколько МР-ов открыто,
сколько из них уже заапрувлено и ждёт отгрузки, сколько висит с незакрытыми
замечаниями, возраст самого старого. Это пласт работы, который иначе теряется:
он сделан внутри периода, но результата в мастере ещё не дал. Не подавай как
претензию — если МР ждёт поезда, это про процесс.}

{Техдолг — есть ли МР-ы типа "техдолг" или "рефакторинг"?
Ответственно ли относится к закрытию тикетов техдолга?}

{Зоны роста — конкретные паттерны из анализа кода, которые стоит улучшить.
Приведи примеры из МР-ов (ссылки на конкретные МР-ы).
Формулируй конструктивно, а не просто "плохо".}
```

**Принципы написания:**

- Пиши на русском, от первого лица (как будто ты — тимлид, который делал ревью)
- Группируй задачи по смыслу, а не перечисляй МР-ы
- Каждое утверждение подкрепляй примером (ссылка на МР или цитата из комментария);
  для замечаний о коде источник — только пункты, прошедшие гейт выше
- Избегай общих фраз без подтверждения — "пишет хороший код" бесполезно без примера
- Не перечисляй все МР-ы — выдели ключевые паттерны
- Если пользователь дал контекст в Step 1 — учти его при расстановке акцентов
- Вывод — inline в чате, не создавай файлы

## Ограничения

- В окно попадает МР с активностью внутри периода в любом состоянии; МР без
  движения отсекается, даже если он открыт и числится за разработчиком
- Черновики (`draft`) собираются наравне с остальными открытыми и помечены флагом
- У МР, начатого до периода, lead time включает часы вне окна — это свойство
  метрики, а не ошибка: считается полный путь МР, а не его кусок внутри периода
- Активностью считается и чужая нота на МР разработчика: ревьюер, вернувшийся к
  старому МР, втягивает его в отчёт. Смотри `activity_reasons`, если состав выборки
  выглядит неожиданно
- `multi_mr_tasks` группирует по ключу тикета в имени ветки: если команда не
  называет ветки по тикету, группировка выродится в совпадение имён веток
- Комментарии от ботов (deployer, ci-*, *bot*) автоматически фильтруются
- Диффы обрезаются до 500 строк на файл — для очень больших МР-ов анализ может быть неполным
- Батчи Step 3 идут на `haiku` ради экономии контекста на диффах; качество кода
  оттуда попадает в отчёт только через гейт по якорям в Step 4. Массовая
  выбраковка — это не повод перезапускать батч (перезапуск съедает всю экономию) и
  не повод ослаблять гейт: раздел о коде просто выходит короче, и это честно
- Скилл не имеет доступа к Jira/Linear/трекеру задач — только GitLab
- Время реакции считается по не-мерж коммитам в МР: если разработчик правил под
  другим именем/почтой или в другом МР, метрика занижена — смотри `warnings` и
  `commit_signatures`
- Rebase переписывает `committed_date`: скрипт ловит расхождение с `authored_date`
  и пишет в `warnings`; у таких МР волны и время реакции недостоверны
- Рабочие часы зашиты как пн–пт 10:00–19:00 в зоне `--tz-offset`; праздники и
  отпуска не учитываются
- Разрез lead time держится на двух конвенциях инстанса: апрув текстом «аудит ок»
  и метка отгрузки нотой `.`. Нет их — есть только общий lead time, разрез пустой
