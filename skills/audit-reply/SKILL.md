# Audit Reply

По каждому замечанию решить с пользователем: **FIX** (правим код) или **REPLY** (обоснование без
правки). Правки — только после явного согласия.

- **Вход**: ссылка на MR (`https://host/group/project/-/merge_requests/41` или `project + iid +
  hostname`) / путь к `.md`|`.txt` / текст в инвокации. Репозиторий склонирован локально.
- **Выход (draft-only)**: правки в рабочем дереве + черновики ответов. Не постить и не резолвить
  в GitLab. Не делать `git add`/`commit`/`push`.
- **Нужно**: локальный чекаут того же проекта; для MR — `glab`, авторизованный на нужном инстансе
  (ошибка → подсказать `glab auth status|login --hostname <host>`), и Python 3.9+.

## Step 1. Собрать замечания

Схема треда одна для всех источников: `author`, `body`, `file` + `new_line` (может отсутствовать),
ответы. Несколько источников сразу — спроси, что разбираем, не объединяй.

### A. Ссылка на MR

SKILL_DIR — абсолютный путь из строки `Base directory for this skill: <путь>`, не cwd:

```bash
python3 "SKILL_DIR/scripts/fetch_mr.py" --url "<MR_URL>"
```

JSON: мета (`source_branch`, `target_branch`, `author`) + `threads` (открытые). Резолвленные
пропускаются (`skipped_resolved`), `--all` включает их. Фильтры: `--author <username>`, `--today`,
`--since YYYY-MM-DD`. Sanity-check: `open_total_before_filter`, `filtered_out_by_author`,
`filtered_out_by_date`.

Сводка: `N открытых тредов в MR "<title>" (<source> → <target>), пропущено резолвленных: M`.

### B. Файл-отчёт / C. Текст в инвокации

Парси сам, скрипта нет. Одно замечание = один тред:

- заголовок находки / пункт списка → `body` целиком, вместе с цитатой кода;
- `file:line` из тела → позиция; нет позиции → `is_general: true`;
- автор — из файла, иначе «ревьюер»; язык ответа — по языку замечания;
- вложенные комментарии → ответы в треде.

Сводка: `N замечаний из <путь>`.

### Общее

- B/C: границы замечания или файл неочевидны → покажи разбивку и спроси, не додумывай.
- Число не сошлось с названным пользователем → скажи о расхождении (MR — фильтр/резолв;
  файл/текст — разбивка). 0 замечаний → сообщи и остановись.

## Step 2. Сверить ветку

- `git rev-parse --abbrev-ref HEAD` против `source_branch`. Не совпало — предупреди и спроси
  (`git switch <source_branch>` или продолжить), не переключай молча.
- B/C без меты — скажи, на какой ветке стоишь, спроси базу диффа.
- База диффа: приоритет за явно названной пользователем (часто родительская фича-ветка), иначе
  `target_branch`. `master` не хардкодь.
- Дифф: `git diff <base>...HEAD` (`--stat` для обзора).

## Step 3. Разобрать каждое замечание

`file` + `new_line` — отправная точка, но **номеру строки не верь**: ищи по содержимому (имя
символа, цитата кода).

Навигация — **LSP** (`hover`, `goToDefinition`, `findReferences`/`incomingCalls`,
`outgoingCalls`), греп только локатор.

**Тредов ≳4 — параллель**: субагент на тред или батч, обязательно `model: "sonnet"` отдельным
параметром в каждом вызове `Agent` (иначе наследуется opus). Дай субагенту `Read`, `Bash`
(`grep`/`rg`/`find` — тулы `Grep` в сборке нет) и **`LSP`**. ≲3 — инлайн.

Каждый разбор:

1. **Суть** — что просит аудитор, 1–2 строки.
2. **Код по делу** — файл:строка, фрагмент, окружение (определение, вызовы, тип).
3. **Оценка** — валидно / частично / нет, почему. Опора на код и конвенции репозитория
   (lint-конфиг, существующие паттерны), не на вкусовщину.
4. **Рекомендация** — **FIX** / **REPLY** (решено иначе / вне скоупа / аудитор ошибается /
   осознанный компромисс) / **DISCUSS** (решает пользователь). Аудитор ошибся из-за того, что код
   не показывает своего инварианта → к ответу идёт комментарий в код (Step 5).
5. **Заготовка действия** — FIX: набросок правки; REPLY: черновик ответа.

## Step 4. Решить по каждому (интерактивно)

Таблица-обзор, строка на тред:

```
| # | Файл:строка | Замечание (кратко) | Оценка | Рекомендация |
```

Дальше `AskUserQuestion`, вопрос на тред, рекомендованный вариант первым с «(рекомендую)»:

- **Править** — в описании: что и где меняем.
- **Ответить** — в описании: черновик ответа **на языке коммента**. С комментарием в код (Step 5)
  вариант называется «Ответить + пояснить в коде», текст комментария виден в описании/`preview`.
  Без этого выбора комментарий в код не вносится.
- **Обсудить** — в описании: что именно неоднозначно.

`header` ≤12 символов: `файл:строка` или `Тред N`. Патч/ответ с кодом — в `preview`.
Не переходи к Step 5 без решения по каждому треду; исключение — «по всем по рекомендации».

## Step 5. Выполнить согласованное

Сначала todo-список сессии (`TaskCreate`/`TodoWrite`): задача на каждый FIX, на каждый
комментарий-в-код, на оформление ответов. Статусы по ходу, одна задача в работе. Только потом
первая правка.

- **FIX** — хирургичная правка в рабочее дерево по конвенциям репозитория, язык любой
  (ts/tsx/css/twig/php/go). К каждой — черновик-уведомление в тред («Поправил: …»).
  - **Чини паттерн целиком**: замечание про повторяющийся косяк → прогони весь дифф ветки, найди
    аналогичные места (`findReferences`, не только греп), покажи список, предложи поправить все.
- **REPLY** — черновик ответа: вежливо, технически, по сути, **на языке комментария**.
  Plain-текст в терминал (не блок-цитата), чтобы копировалось.
  - Ответ «код и так корректен» опирается на невидимый в коде инвариант (гарантия из вызывающего
    кода, порядок инициализации, ограничение бэкенда, неожиданный тип) → предложи **однострочный
    комментарий рядом** с тем же инвариантом:
    - без истории правки: ни «ревьюер спрашивал», ни «оставлено как есть», ни ссылок на MR;
    - один комментарий на инвариант, там, где на него натыкаются;
    - **не для всех REPLY**: вне скоупа, «поправим в следующем MR», вкусовщина, спор о фактах вне
      этого кода — не нужен. Нерешённый инвариант — тикет и ссылка на него;
    - инвариант выразим в коде (имя, тип, вынесенный предикат) — предложи это как FIX.
- **DISCUSS** — не закрывай сам, зафиксируй вопрос и варианты.

После всех FIX — проверка: доступные typecheck/lint/тесты либо перечитать изменённые места и их
вызовы через LSP. Правки в нескольких файлах — сверь сигнатуры с местами вызова.

## Step 6. Итоговый отчёт

В чат; в файл `audit-reply-MR<iid>.md` — только по явной просьбе.

```markdown
## Правки (FIX)
- `<file>` — <что сделано>. Черновик в тред: «<уведомление>»

## Ответы без правок (REPLY)
### <file:line> — <автор>
> <цитата замечания>

<черновик ответа на языке комментария>
<если добавлен комментарий в код: «Плюс комментарий в `<file>`: <текст>»>

## К обсуждению (DISCUSS)
- <вопрос + варианты>
```

Напомни: правки в рабочем дереве, не закоммичены (включая комментарии к REPLY); ответы —
черновики; постинг и резолв — за пользователем.

## Пограничные случаи

- **glab не авторизован / не тот host** — внятная ошибка + `glab auth login` (только MR).
- **Отчёт без позиций** — разбирай по смыслу диффа, позицию не выдумывай.
- **Замечание не находится в коде** — отчёт устарел или по другой ветке: скажи и спроси, не
  подгоняй под похожее место.
- **Номер строки устарел** — ищи по содержимому, отметь расхождение в разборе.
- **`is_general: true`** — якоря нет, разбирай по смыслу всего диффа.
- **`is_author_self: true`** — заметка автора, не замечание: контекст или пропуск.
- **Несколько ревьюеров** — атрибутируй ответы по автору треда.
- **`reply_count > 0`** — учитывай переписку, не повторяй сказанное.
