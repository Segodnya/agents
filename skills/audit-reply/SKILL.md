# Audit Reply

Ты помогаешь автору MR разобраться с замечаниями ревьюера (аудитора): по каждому
открытому комментарию решить — **править код** или **ответить обоснованием**, почему
правка не нужна. Решение принимается ВМЕСТЕ с пользователем: твоя задача — собрать
факты, дать честную оценку и рекомендацию, а финальный выбор за ним.

Главное: ты не угадываешь намерение аудитора и не правишь молча. Сначала разбираешься
в коде, потом показываешь таблицу решений, и только после явного согласия пользователя
применяешь правки и пишешь ответы.

## Что на входе и на выходе

- **Вход:** ссылка на MR (`https://host/group/project/-/merge_requests/41`) либо
  `project + iid + hostname`. Репозиторий уже склонирован локально.
- **Выход (draft-only):** применённые в рабочем дереве правки + черновики ответов
  аудитору. В GitLab скилл **сам ничего не публикует и не резолвит** — ты копируешь
  ответы и постишь сам. Не делай `git add`/`commit`/`push`.

## Prerequisites

- `glab` CLI установлен и авторизован на нужном инстансе. Если падает чтение MR —
  подскажи: `glab auth status --hostname <host>` / `glab auth login --hostname <host>`.
- Python 3.9+ (для скрипта сбора).
- Локальный чекаут того же проекта, что в ссылке.

## Workflow

### Step 1. Собери открытые треды

Запусти скрипт (SKILL_DIR — абсолютный путь к этому скиллу из строки
`Base directory for this skill: <путь>`, не угадывай и не используй cwd):

```bash
python3 "SKILL_DIR/scripts/fetch_mr.py" --url "<MR_URL>"
```

Скрипт вернёт JSON: мету MR (`source_branch`, `target_branch`, `author`) и массив
`threads` — открытые (нерезолвленные) треды с автором, телом, `file`/`new_line` и
ответами в треде. Резолвленные треды по умолчанию пропускаются (их число — в
`skipped_resolved`); если нужно разобрать всё, добавь `--all`.

**Применяй фильтры под формулировку пользователя** — аудитор обычно один и часто речь
идёт только о свежих комментариях:

- `--author <username>` — только треды конкретного ревьюера («комментарии kkurentsov»).
- `--today` — только сегодняшние комментарии («посмотри комменты за сегодня»).
- `--since YYYY-MM-DD` — с конкретной даты.

В выводе для sanity-check есть `open_total_before_filter`, `filtered_out_by_author`,
`filtered_out_by_date`.

Покажи пользователю короткую сводку: `N открытых тредов в MR "<title>" (<source> → <target>),
пропущено резолвленных: M`. **Сверь количество**: если пользователь назвал число
(«там три комментария»), а вышло другое — не молчи, скажи о расхождении (возможно, не
тот фильтр по дате/автору, или часть тредов уже резолвлена). Если открытых тредов 0 —
сообщи и остановись.

### Step 2. Сверь ветку

Дифф и соседний код берутся локально, поэтому важно, что на диске именно та ветка.

- Сравни текущую ветку с `source_branch` из меты: `git rev-parse --abbrev-ref HEAD`.
- Если не совпадает — **предупреди и спроси**, прежде чем что-то делать. Не переключай
  ветку молча (это меняет состояние рабочего дерева). Дай выбор: переключиться
  (`git switch <source_branch>`) или продолжить как есть, если пользователь знает, что
  делает (он мог осознанно встать на родительскую/смежную ветку).
- **База диффа — приоритет за явно названной пользователем.** В этих задачах target
  редко `master`: часто это родительская фича-ветка («работаем против `feature/TASK-766`»,
  «diff against `feature/TASK-972`»). Если пользователь назвал базу — бери её; иначе —
  `target_branch` из меты;.
- Дифф бери как `git diff <base>...HEAD` (три точки — то, что изменилось в ветке
  относительно точки расхождения). `--stat` для обзора, по файлам — по мере надобности.

### Step 3. Разберись в каждом комментарии

Для каждого открытого треда нужно понять: на какой код он указывает, что аудитор хочет,
и обоснована ли претензия. Источник истины по позиции — `file` + `new_line` из API, но
**не верь номеру строки слепо**: ветка могла уехать с момента комментария. Находи место
по содержимому (имя функции/символа рядом), а не только по номеру строки.

Для навигации по коду используй **LSP**, а не греп по имени символа: `hover` — реальный тип/доки, `goToDefinition` — где определён, `findReferences`/`incomingCalls` — кто использует, `outgoingCalls` — что
зовёт сам символ. Греп — только локатор позиции. Так оценка будет основана на реальном
коде, а не на догадке по диффу.

**Параллелизуй**, когда тредов много (≳4): спавни по субагенту на тред (или батч),
каждый возвращает структурный разбор (ниже). Дай субагентам доступ к `Read`/`Grep` и
**`LSP`** — без навигации они будут гадать. При ≲3 тредах разбирай инлайн.

Каждый разбор (свой/субагента) содержит:

1. **Суть замечания** — что аудитор просит, в 1–2 строки.
2. **Код по делу** — файл:строка, фрагмент, и что вокруг (определение, вызовы, тип).
3. **Оценка** — претензия валидна / частично / нет; почему. Опирайся на код и
   конвенции репозитория (lint-конфиг, существующие паттерны), а не на вкусовщину.
4. **Рекомендация** — одно из:
   - **FIX (править)** — претензия по делу, меняем код.
   - **REPLY (ответить)** — правка не нужна (уже решено иначе / вне скоупа / аудитор
     ошибается / осознанный компромисс) → нужен ответ-обоснование.
   - **DISCUSS (обсудить)** — реально неоднозначно, решает пользователь.
5. **Заготовка действия** — для FIX: набросок правки (какой файл/что меняем); для REPLY:
   черновик ответа.

### Step 4. Реши по каждому комментарию (интерактивно)

Сначала покажи таблицу-обзор — по строке на тред, чтобы было видно всю картину разом:

```
| # | Файл:строка | Замечание (кратко) | Оценка | Рекомендация |
```

Затем **собери решения через `AskUserQuestion`**, а не свободным текстом — так пользователю
быстрее выбрать, и решение фиксируется явно. По одному вопросу на тред, варианты:

- **Править (рекомендую)** — в описании: что и где меняем (короткий набросок правки).
- **Ответить** — в описании: черновик ответа аудитору **на языке коммента**.
- **Обсудить** — в описании: что именно неоднозначно.

Рекомендованный вариант ставь первым с пометкой «(рекомендую)». Смысл — в каждом варианте
пользователь сразу видит, что конкретно получит при этом выборе: и сам патч, и
альтернативный ответ. Для патча/ответа с кодом удобно положить текст в `preview`.

Практика:
- Тредов много — `AskUserQuestion` на каждый вопрос.
- `header` — короткая привязка (≤12 симв.): `файл:строка` или `Тред N`.
- Не переходи к Step 5, пока по каждому треду нет явного решения. Если пользователь сам
  сказал «по всем — по рекомендации», вопросы можно пропустить.

### Step 5. Выполни согласованное

**Сначала зафиксируй план как todo-список сессии** (`TaskCreate`/`TodoWrite`) — это
чек-поинт перед тем, как трогать файлы: по задаче на каждый согласованный FIX и на
оформление ответов (REPLY/DISCUSS). Зачем: видно согласованный объём, ничего не теряется
на длинной сессии, и пользователь следит за прогрессом. Дальше отмечай статусы по ходу
(`in_progress` на старте задачи → `completed` по завершении), по одной задаче в работе
за раз. Только после создания списка начинай первую правку.

- **FIX** — внеси правку в рабочее дерево. Хирургично: трогай только то, что относится к
  замечанию, соблюдай конвенции репозитория (lint-конфиг, существующие паттерны, SRP).
  Не завязывайся на язык — это может быть фронт (ts/tsx/css/twig) или бэк (php/go).
  К каждой правке — короткий черновик-уведомление в тред («Поправил: …»).
  - **Чини паттерн целиком, а не одну строку.** Если замечание про повторяющийся косяк
    (одинаковая ошибка, антипаттерн), прогони весь дифф ветки и найди **аналогичные места
    в других файлах/строках**. Покажи список найденного и предложи поправить все вхождения
    — ревьюер ждёт исправления паттерна, а не точечной заплатки. Навигацию веди через LSP
    (`findReferences`), не только грепом.
- **REPLY** — черновик ответа аудитору: вежливо, технически обоснованно, по сути.
  **Язык ответа — как в самом комментарии** (рус → по-русски, en → по-английски).
  Используй plain-текст в терминал, а не текст, оформленный как цитаты,
  чтобы его было удобно копировать.
- **DISCUSS** — не закрывай сам; зафиксируй вопрос и варианты, реши с пользователем.

После всех FIX-правок **проверь, что логика не нарушена**: прогони доступные проверки
(typecheck/lint/тесты, если есть в репозитории) либо перечитай изменённые места и их
вызовы через LSP. Если правок касались несколько файлов — особенно сверь, что сигнатуры
и контракты не разъехались с местами вызова.

### Step 6. Итоговый отчёт

Собери результат в таком виде (можно сохранить в файл `audit-reply-MR<iid>.md` рядом,
чтобы было что копировать в GitLab - если пользователь об этом явно попросит; иначе -
вывод в чат сессии):

```markdown
## Правки (FIX)
- `<file>` — <что сделано>. Черновик в тред: «<уведомление>»

## Ответы без правок (REPLY)
### <file:line> — <автор>
> <цитата замечания>

<черновик ответа на языке комментария>

## К обсуждению (DISCUSS)
- <вопрос + варианты>
```

Напомни: правки уже в рабочем дереве (не закоммичены), ответы — черновики, постинг и
резолв тредов — за пользователем.

## Пограничные случаи

- **glab не авторизован / не тот host** — внятная ошибка + команда `glab auth login`.
- **Ветка не совпадает** — предупреди, не переключай молча (Step 2).
- **Номер строки устарел** (тред помечен на изменившемся коде) — ищи по содержимому,
  отметь расхождение в разборе.
- **Общий комментарий MR без позиции** (`is_general: true`) — нет якоря в коде; разбери
  по смыслу всего диффа.
- **Комментарий самого автора** (`is_author_self: true`) — это не замечание ревьюера, а
  заметка автора; не предлагай «ответить себе», используй как контекст или пропусти.
- **Несколько ревьюеров** — атрибутируй ответы по автору треда.
- **Тред с ответами** (`reply_count > 0`) — учитывай переписку: возможно, часть уже
  прояснена; не повторяй то, что уже сказано.
- **База диффа** — приоритет за явно названной пользователем, иначе `target_branch` из
  меты; `master` не хардкодь (см. Step 2).
