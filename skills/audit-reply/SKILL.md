# Audit Reply

**Суть:** по каждому замечанию — либо правка, которая закрывает его целиком и ничего не ломает рядом,
либо ответ, который ревьюер примет без второго круга. Плохой исход в обе стороны один: тот же тред
возвращается следующим раундом.

- **Вход**: ссылка на MR / путь к `.md`|`.txt` / текст в инвокации. Репозиторий — локальный чекаут.
- **Выход**: правки в рабочем дереве + черновики ответов. В GitLab ничего не постится и не резолвится.
- **Режимы.** По умолчанию интерактивный: решение по каждому треду — за пользователем, без `git add`/`commit`.
  Флаги `mr-ready`: `--auto` — решаешь сам по рекомендации, спорное → `discuss.md`; `--commit` — FIX
  коммитится после зелёных проверок; `--base <branch>`; `--ar-dir <path>`; `--checks <file>` — как
  в этом репо запускаются проверки; `--checklist <file>` — чек-лист
  отгрузки, который FIX обновляет сам (см. «Чек-лист»); `--spec <file>` — ТЗ тикета; `--threads <file>` — треды
  уже собраны вызывающим в формате `fetch_mr.py`: читаешь этот файл вместо GitLab.

`SKILL_DIR` — путь из строки `Base directory for this skill:`. `AR_DIR` — `--ar-dir`, иначе
`/tmp/audit-reply-<repo>-<branch>`; под `--auto` без `--ar-dir` сначала `rm -rf` (старый `replies.json`
смешается с новым). Пути подставляй литералами: состояние шелла между вызовами не живёт.

## 1. Собрать замечания

MR:

```bash
python3 "SKILL_DIR/scripts/fetch_mr.py" --url "<MR_URL>" > AR_DIR/threads.json
python3 "SKILL_DIR/scripts/read_threads.py" AR_DIR/threads.json          # индекс
python3 "SKILL_DIR/scripts/read_threads.py" AR_DIR/threads.json 3 7 12   # тела целиком, одним вызовом
```

`--threads <file>` → вместо `fetch_mr.py` — `cp <file> AR_DIR/threads.json`, дальше так же. Id треда вида `L<n>` —
локальная находка mr-ready: в GitLab её нет, ответ на неё — та же строка `replies.json`.

Индекс — чтобы выбрать, тела — чтобы судить: форму правки ревьюер часто диктует в хвосте треда, не
обрезай. Тред называй `T<n> · <id[:8]>` (номер меняется между запусками, id — нет).
`last_by_author: true` — мяч у ревьюера: под `--auto` такой тред не берёшь, если вызывающий не назвал
его явно. `🤖 self-review ·` — находка mr-ready под аккаунтом автора, разбирай как замечание. Ноты
ботов скрипт уже отсёк. Нужна часть тредов → фильтры в `fetch_mr.py --help`.

Файл / текст: одно замечание = один тред (`body`, `file:line` если есть, автор, ответы). Границы
неочевидны → покажи разбивку и спроси.

## 2. База и дифф

- Ветка ≠ `source_branch` → предупреди и спроси (под `--auto` — в `discuss.md`), не переключай молча.
- База — `--base` или названная пользователем, иначе `target_branch`; дифф `git diff <base>...HEAD`.
- Path-scoped правила репо сами в контекст не попадают — собери:
  `git diff <base>...HEAD --name-only | python3 "SKILL_DIR/../review-staged/scripts/match_rules.py" <repo-root> --rule-files-out AR_DIR/rule-files.txt > AR_DIR/rules.md`.
  Читай из них то, что относится к файлам разбираемых тредов.

## 3. Разбор: что проверить

Номер строки треда — отправная точка, не истина: ищи по содержимому. Навигация — греп
по умолчанию («где объявлено» — тоже греп); LSP — только список потребителей (`findReferences`, `incomingCalls`)
и тип выражения (`hover`).

Перед решением ответь себе на вопросы — они и есть работа:

1. **Что именно не так** и где это видно: строка якоря, её функция, её вызывающие.
2. **Где ещё то же самое.** Близнец — тот же паттерн (матчер, вызов, скопированный блок) или другая
   строка с тем же дефектом: нарушает то же правило из `rules.md` или подходит под суть треда (JSDoc
   пересказывает вызывающего, свойство вида не названо в чек-листе). Граница — дифф и файлы, которые он трогает: паттерн
   ищешь грепом, правило проверяешь на каждой строке диффа в этих файлах. Правишь каждого близнеца в
   границе; близнец вне границы — по п. 3 (тикет).
3. **Причина или симптом.** Замечание называет пример («считается дважды») — найди, что делает его
   неверным или дорогим, и правь там. Причина вне диффа → правишь, только если это функция,
   которую дифф уже тронул; иначе тикет.
4. **Что сломает правка.** Все вызывающие, парная операция (open/close, add/remove, save/load —
   та же правка), каждый вид входа (пусто/null, повтор, каждое состояние, поздний или
   конкурентный вызов), контракт с другими слоями.
5. **Прав ли ревьюер.** Опора — код, правила из `rules.md` (цитата дословно), решения `S<n>` из
   `### Settled` описания MR (`description` в `threads.json`), конвенции репо; не вкус. Комментарий в
   коде и отчёт субагента — гипотезы, проверь.

Итог разбора: **FIX** / **REPLY** (решено иначе, вне скоупа, ревьюер ошибся, осознанный компромисс) /
**DISCUSS** (решает человек). Нарушение правила проекта, подтверждённое цитатой, — только FIX или
DISCUSS: «соседи нарушают так же» и «вынесу отдельным MR» — не довод. Замечание оспаривает `S<n>`, и
ссылки на него в треде ещё нет → REPLY «Решено: S<n>, раздел Settled в описании MR»; ссылка уже есть,
а последнее слово не за автором → DISCUSS. Цитату правила проекта Settled не перекрывает.

## 4. Решение

**Интерактивно** — таблица `| # | файл:строка | суть | оценка | рекомендация |`, затем
`AskUserQuestion` на тред, рекомендованный вариант первым: «Править» (что и где) / «Ответить»
(черновик на языке треда; с комментарием в код — «Ответить + пояснить в коде») / «Обсудить». К
выполнению — только после решения по каждому или «по всем по рекомендации».

**`--auto`** — FIX и REPLY исполняешь сам. Контракт — чек-лист (`--checklist`), ТЗ (`--spec`) и `S<n>` из
`### Settled`. В `AR_DIR/discuss.md` — **только вопросы к человеку**
(строка на тред: `- T<n> · <id[:8]> · file:line — суть, варианты, рекомендация`), по триггеру:

- правка меняет видимое поведение, вёрстку или текст для пользователя не так, как записано в контракте;
- правка меняет внешний контракт: API, формат данных или хранения, ключи конфига, env, CLI-флаги;
- несогласие с тредом человека, не опровергаемое кодом или правилом;
- правка добавит видимое поведение, о котором контракт молчит → не правишь, строка с пометкой «вне контракта».

Остальное решаешь сам:

- правка выходит за скоуп тикета → REPLY «вне скоупа» + черновик тикета в финальном ответе;
- REPLY оставляет дубль компонента, FIX тянет переименования → по рекомендации;
- логика меняется, а тест написать нельзя → как в «Тест»;
- `🤖 self-review · Design note:` и любая находка об устройстве кода, а не о поведении (дубль, литерал,
  имя, раскладка модулей) → FIX, только если правка убирает код или укорачивает путь, не добавляет файл,
  модуль или публичный экспорт и не меняет ни поведение, ни контракт; иначе REPLY «оставляю ревьюеру:
  <одна фраза почему>».

Финальный ответ — всё прочее; непустой `discuss.md` для mr-ready означает вопрос пользователю.

## 5. Выполнить

Несколько FIX → todo-список до первой правки.

**FIX** — хирургично, по конвенциям репо; новый файл/абстракция — только если тред её просит, иначе
REPLY с вариантом или DISCUSS. Комментарии и doc-блоки в новых строках — как велят `rules.md` и
соседний код; правила молчат → без комментария, кроме инварианта для REPLY (ниже).

- **Тест.** Логика меняется → тест в том же коммите; что он красный без правки, ты видел прогоном.
  Ожидаемое значение берётся из независимого источника: поведение базы (`git show <base>:…`, прогон
  старого кода), ТЗ, чек-лист, решение пользователя, тело треда. Тест проверяет поведение через
  публичный вход. Значение, снятое с кода, и чтение обратно записанного в стор — тавтология: такой
  тест не пишешь, пункт чек-листа получает «вручную», в ответе — «ожидание есть только в коде».
  Тест невозможен → под `--auto` гвард/null-check/ранний return без смены контракта — FIX при зелёных
  проверках, иначе REPLY «нет способа покрыть тестом». Код, который исполняется не в твоём шелле (CI-джоб,
  контейнер, cron, удалённый хост), проверяется прогоном в его среде (строка `Среда:`), не локально.
- **Якорь закрыт.** После правки строка, на которой висит тред, изменилась — или в ответе одной
  фразой, почему правка в другом месте закрывает и её.
- **Близнецы закрыты.** Тело FIX кончается строкой `близнецы: file:line, …` (поправлены в том же коммите)
  или `близнецы: нет · <команда грепа>`. Без этой строки FIX не готов.
- **Свои строки по правилам.** Перед коммитом пройди `git diff` своей правки по каждому правилу из
  `rules.md`, чей путь матчит её файлы. Готово, когда ни одну добавленную строку нельзя процитировать
  с правилом как нарушение.
- **Чек-лист** (`--checklist`). FIX меняет то, что тестировщик по чек-листу увидит или должен сделать
  (поведение для пользователя или клиента API, шаг отгрузки: рестарт, миграция, сброс кэша) → правишь
  пункт файла: «было → стало», новый кейс — новым пунктом в той же секции. Тред с меткой `· чек-лист`
  (в диффе, не обещано) — FIX только пунктом чек-листа, код не меняется. Каждую правку файла — строкой
  `чек-лист: п.<n> · было «…» → стало «…»` в финальный ответ. Файл вне репо, в `git add` не идёт.
- **Проверки** — после каждого FIX, из корня репо:
  `python3 "SKILL_DIR/../mr-ready/scripts/run_checks.py" <файл из --checks> AR_DIR` (без флага — typecheck /
  lint / тесты репо по файлам правки, бинарями напрямую, не через таск-раннер). Логи — в `AR_DIR`.

**`--commit`**, проверки зелёные:
1. Сообщение в стиле `git log --oneline -10`, в теле `file:line` треда → `AR_DIR/msg-<n>.txt`.
2. Из корня репо: `python3 "SKILL_DIR/scripts/check_commit_msg.py" AR_DIR/msg-<n>.txt`.
3. `git add <файлы правки>` + `git commit -F AR_DIR/msg-<n>.txt > AR_DIR/commit-<n>.log 2>&1`. Хук упал →
   причина (имя теста, правило линтера) — из этого лога целиком, `grep -n 'FAIL\|✖\|error'` по нему.

Красно (проверки или шаг 2) → одна попытка; снова красно → `git checkout -- <файлы>`, REVERTED
«попробовал, откатил: <причина>». Без `push`, `--amend`, `rebase`.

**REPLY** — довод, почему оставляем, на языке треда. Ревьюер ошибся, потому что код не показывает
инварианта (гарантия вызывающего, порядок инициализации, ограничение бэка) → однострочный
комментарий рядом с инвариантом, без истории правки; выразим в коде (имя, тип, предикат) → это FIX.
Факт из истории («было до ветки») — только подтверждённый `git log`/`blame`.

**Текст в тред** — 1–2 предложения, без кода и перечня проверок. FIX: «Поправил в `<hash>`» + полфразы
как, если неочевидно по коммиту.

### `AR_DIR/replies.json` (`--auto`)

Только через скрипт, из корня репо:

```bash
python3 "SKILL_DIR/scripts/reply_add.py" AR_DIR/replies.json <discussion_id> FIX "Поправил в <hash>." "<команда>" "git log -1 <hash>"
```

Хвостовые аргументы — `verified_by`: команды, подтверждающие каждый факт тела. Скрипт их выполняет
и откажет, если хоть одна красная или не запускается. Формат — как строка `--checks` (см. docstring
`mr-ready/scripts/run_checks.py`), можно суженная до своих файлов.

## 6. Отчёт

Интерактивно — в чат: FIX (файл, тред, что сделано, черновик уведомления), REPLY (цитата замечания +
черновик ответа), DISCUSS (вопрос + варианты); напомни, что правки не закоммичены и постинг за
пользователем. Под `--auto` — финальный ответ вызывающему в формате из его промпта, одним
`SubagentHandback` после коммитов и `replies.json`.

## Пограничные случаи

- Замечание не находится в коде → отчёт устарел или другая ветка: скажи, не подгоняй под похожее.
- В треде уже есть переписка → учитывай её, не повторяй сказанное.
