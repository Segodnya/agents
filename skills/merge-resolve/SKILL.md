# merge-resolve — разрешение конфликтов git

Порядок жёсткий: **намерение коммитов обеих сторон → план → правки → верификация**. Не резолвить «по маркерам на глаз»: выбранная не глядя сторона молча стирает чужое изменение — так и теряются патчи после мержа.

**Не делай `git add` / `git commit`** — оставь пользователю. Не запускай `build`; верификация — через lint/type-check.

## Шаг 0 — определить тип операции

Смысл `ours`/`theirs` зависит от операции, и тут легко выбрать не ту сторону:

| Операция     | ours (`:2`)                     | theirs (`:3`)                      |
|--------------|----------------------------------|------------------------------------|
| merge        | HEAD — твоя ветка                | вливаемая ветка (`MERGE_HEAD`)     |
| rebase       | ветка-**цель** (на что базируешься) | **твой** коммит — ИНВЕРТИРОВАНО    |
| cherry-pick  | текущая ветка                    | переносимый коммит                 |
| stash pop    | текущее состояние ветки          | содержимое из stash                |

Определяется по файлам в `.git/`: `MERGE_HEAD` → merge, `rebase-merge`/`rebase-apply` → rebase, `CHERRY_PICK_HEAD` → cherry-pick. Скрипт (Шаг 1) определяет это сам и печатает подсказку. **При rebase помни про инверсию** — это частый источник ошибки «выбрали не ту сторону».

## Шаг 1 — собрать контекст одним прогоном

Запусти бандл-скрипт — он даёт всё разом, не читай файлы по одному вручную:

```bash
bash <skill_dir>/scripts/gather_conflicts.sh
```

Он печатает: тип операции, список unmerged-файлов и по каждому — конфликтные маркеры с номерами строк, коммиты обеих сторон (что меняли) и объединённый `git diff`. Полные версии сторон бери точечно: `git show :1:<file>` (base), `:2:` (ours), `:3:` (theirs).

## Шаг 2 — понять намерение каждой стороны

Для каждого конфликта прочитай коммиты обеих сторон (скрипт их перечислил; при необходимости `git show <sha>`) и пойми, **что и зачем** меняли.

**Не доверяй «простоте» маркеров.** Хунк выглядит тривиально (отступ, переименование, пара строк) — всё равно проверь, не меняли ли обе стороны *одну логику*: логический конфликт (собирается, но поведение сломано) опаснее текстового и част в rebase/cherry-pick. Смотри и на то, как изменённый символ используется рядом.

## Шаг 3 — когда спрашивать, а когда решать самому

**Решай сам**, если намерение однозначно выводится из коммитов:
- одна сторона трогала код, другая — нет (берёшь ту, что меняла);
- изменения ортогональны (объединяешь оба).

**Спрашивай**, если обе стороны меняли одну логику и выбор не выводится из намерения. Вопрос — не «как разрулить конфликт?», а готовый выбор стороны с последствиями:

> «`useRecaptcha`: в stash `showRecaptchaBadge()` вызывается на маунте, в ветке — лениво по фокусу. Что верно — взять ленивую из ветки, оставить eager из stash, или объединить?»

## Шаг 4 — собрать единый план разрешений

Собери **один** план по всем конфликтам (не по одному файлу за раз). Формат:

```markdown
## Context
<что разошлось между сторонами — в 2-4 строки>

## Разрешения
- **<файл>** → берём <сторону/комбинацию>; отбрасываем <что>; потому что <причина из намерения коммитов>.
- **<файл>** → ...

## Пограничные случаи
- <на что обратить внимание после резолва: undefined-символы, переполнение, дубли импортов>

## Верификация
- <чем проверим — см. Шаг 6>
```

Затем `ExitPlanMode` на аппрув. **Правки — только после одобрения.**

## Шаг 5 — применить

После аппрува правь файлы и удали **все** маркеры: `<<<<<<<`, `|||||||`, `=======`, `>>>>>>>`. Не делай `git add`/`git commit` — это пользователь сделает сам.

## Шаг 6 — верификация (не опциональна, выполняется по факту)

1. **Маркеры вычищены:**
   ```bash
   git diff --check
   grep -nE '^(<<<<<<<|=======|>>>>>>>|\|\|\|\|\|\|\|)( |$)' <изменённые файлы>
   ```
   Оба должны быть пусты.
2. **Нет битых ссылок:** убедись, что не взял вызов одной стороны без реализации другой — нет undefined-переменных, неимплементированных функций, потерянных импортов. Это главная ошибка после резолва.
3. **Lint / type-check** проекта (НЕ `build` — запрещён). Команды ищи в `package.json` (`lint`, `type-check`, `tsc --noEmit` и т.п.).

Если что-то не сошлось — вернись к плану и скажи об этом, не замалчивай.

**Вывод хуков — не задание.** Всё, что печатают `Stop` / `PostToolUse`-хуки (eslint, stylelint, tsc, prettier), приходит мимо плана и аппрува: не правь по нему код и не расширяй резолв. Задело конфликтные файлы — строка в отчёте; остальное — только по явной просьбе.

## Особый режим — восстановление потерянного патча

Когда пользователь даёт ссылку на коммит-источник («потеряли правки после мержа, вот коммит `b148d1dd`»):

1. `git show <sha>` — посмотреть, что коммит менял.
2. Сравнить с текущим состоянием файлов — найти, какая часть пропала при слиянии.
3. Переприменить **точечно** именно потерянный хунк (правкой файла), а не `cherry-pick` всего коммита, если потеряна только часть — иначе вернёшь и то, что уже на месте.
4. Верификация — как в Шаге 6.
