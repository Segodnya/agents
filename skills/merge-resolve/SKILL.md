# merge-resolve — разрешение конфликтов git

Порядок: **классификация → намерение коммитов → структурная сверка → план → аппрув → правки → верификация** (→ стейдж по просьбе).

Не делай `git add` / `git commit`. Исключения:
- удаление файла по плану (delete/modify, `both-deleted`, сирота с аппрувом) резолвится только через `git rm <file>`; сделай и напиши в отчёте, что тронул индекс;
- пользователь просит застейджить резолв — Шаг 7.

Не запускай `build`.

## Шаг 0 — тип операции

| Операция    | ours (`:2`)                         | theirs (`:3`)                  |
|-------------|-------------------------------------|--------------------------------|
| merge       | HEAD — твоя ветка                   | вливаемая ветка (`MERGE_HEAD`) |
| rebase      | ветка-**цель** — ИНВЕРТИРОВАНО      | **твой** коммит                |
| cherry-pick | текущая ветка                       | переносимый коммит             |
| stash pop   | текущее состояние ветки             | содержимое из stash            |

Определяется по `.git/`: `MERGE_HEAD` → merge, `rebase-merge`/`rebase-apply` → rebase, `CHERRY_PICK_HEAD` → cherry-pick. Скрипт Шага 1 печатает это сам. **При rebase стороны инвертированы** — частый источник ошибки.

## Шаг 1 — классифицировать и собрать контекст

```bash
python3 <skill_dir>/scripts/classify_conflicts.py --out "$TMPDIR/merge-resolve"
```

Делит unmerged-файлы на классы и кладёт списки `<класс>.txt` и черновики `drafts/<path>` в `--out`:

- `take-theirs` / `take-ours` — версия одной стороны есть в истории другой, и более новая сторона правила файл своими коммитами: берём её;
- `squash-theirs` / `squash-ours` — каждый собственный коммит одной стороны по файлу лежит в ветке, которую другая сторона влила squash-мержем (GitLab) позже этого коммита. Версия первой стороны — старая копия той же работы до ревью; берём сторону со squash;
- `realbase-clean` — 3-way merge от общей версии файла проходит без конфликтов и не задваивает имён, черновик готов;
- `both-deleted` — файл удалили обе стороны (ренейм на обеих): `git rm`;
- `manual` — разбираешь ты; черновик diff3 от реальной базы, если она есть, короче маркеров `ort`.

Сводка печатает у классов число `git rm`: в take-*/squash-* это файлы, которых нет на оставляемой стороне. План берёт числа отсюда, а не считает руками.

Причина по каждому ручному файлу — `reasons.txt`. Собственные коммиты сторон по ручным файлам, которых не принёс squash другой стороны, — `side-commits.txt`: это готовый список для Шага 2. Коммит из squash-ветки там не нужен: его итог после ревью уже лежит на другой стороне.

Класс `squash-*` не видит правку, сделанную прямо в merge-коммите стороны: перед аппрувом сверь 2–3 файла класса (`git diff MERGE_HEAD HEAD -- <файл>`).

Блок `ОТКАТЫ` — `git revert` в собственном диапазоне одной из сторон. Это развилка в плане до аппрува: принять откат или сохранить откатанное (revert of revert). Файлы отката всегда в `manual`, их черновик построен от версии до отката (`<sha>^`) и принимает откат: в нём остаются только правки другой стороны поверх откатанного кода. Откаченный мерж ветки её коммиты не покрывает.

На сборочных ветках с несколькими merge-base механические классы — бо́льшая часть конфликтов. Их намерение не разбирай по файлу: в план они идут группой. Шаги 2–3 — только для `manual`.

Контекст по `manual`:

```bash
bash <skill_dir>/scripts/gather_conflicts.sh > "$TMPDIR/merge-resolve/gather.txt"
```

Вывод большой — читай секции `ФАЙЛ:` только ручных файлов. Полные версии сторон: `git show ":1:${f}"` (base), `":2:${f}"` (ours), `":3:${f}"` (theirs). Номер стадии или путь в переменной пиши через `${…}`: в zsh `:` после имени переменной — модификатор, и `:$n:frontend/x` превращается в `:2ontend/x`.

## Шаг 1.5 — структурная сверка (до разбора маркеров)

```bash
python3 <skill_dir>/scripts/check_merge_symbols.py
```

Ловит то, что лежит **вне маркеров** и не видно ни tsc, ни eslint, ни jest: `ДУБЛЬ` (авто-мерж вставил вторую копию метода — вторая затирает первую; или задвоил имя в импортах, экспортном списке, полях interface, деструктуризации) и `ПРОПАЛ` (сторона переименовала метод, удаление уехало в неконфликтную зону). Работает и на конфликтном мерже, и на закоммиченном авто-мерже.

Скрипт — регекс-эвристика, вердикт выносишь ты:

- `.ts`/`.tsx` — дубль подтверди грепом по имени, кто остался с вызовом — `LSP findReferences` (сначала `ToolSearch("select:LSP")`, позиция — из `workspaceSymbol` с `query`).
- легаси-Backbone, `.php`, `.js` без типов — LSP не поможет, читай исходник обеих сторон.

Дубль может быть перегрузкой, пропажа — намеренным удалением. Хвост `менял коммит <сторона> <sha> «тема»` у `ПРОПАЛ` — последний коммит другой стороны, менявший имя в файле: пропажи одного коммита (отката, рефакторинга) объясняй в плане одной строкой на коммит. Каждый пункт отчёта объясни в плане (Шаг 4).

Блок `УДАЛЁННЫЕ ЭКСПОРТЫ С ПОТРЕБИТЕЛЯМИ` из Шага 1 — сломанный контракт между сторонами: выбранная версия модуля убрала символ, а файл другой стороны его импортирует. Маркеров тут нет, tsc покажет это только после правок. Каждая строка — развилка в плане до аппрува: оставить модуль другой стороны, адаптировать потребителя или принять поломку.

Отдельно проверь файлы, пришедшие одной стороной целиком (`git diff --name-only <base>..theirs` против ours) — в первую очередь тесты и фикстуры: они молча приносят старый контракт.

## Шаг 2 — намерение сторон

По каждому конфликту прочитай коммиты обеих сторон (`git show <sha>`) и пойми, что и зачем меняли.

Тривиальный на вид хунк (отступ, переименование, пара строк) проверяй так же: логический конфликт — собирается, но поведение сломано — опаснее текстового и част в rebase/cherry-pick. Смотри, как изменённый символ используется рядом.

## Шаг 3 — решать самому или спрашивать

**Сам**, если намерение выводится из коммитов: одна сторона трогала код, другая нет → берёшь ту, что меняла; изменения ортогональны → объединяешь.

**Спрашивай**, если обе стороны меняли одну логику. Вопрос — готовый выбор с последствиями, а не «как разрулить»:

> «`useRecaptcha`: в stash `showRecaptchaBadge()` на маунте, в ветке — лениво по фокусу. Взять ленивую из ветки, оставить eager из stash, или объединить?»

## Шаг 4 — единый план

Один план по всем конфликтам сразу, не по файлу за раз:

```markdown
## Context
<что разошлось между сторонами — 2-4 строки>

## Разрешения
- **take-theirs / take-ours / realbase-clean** → N файлов группой, по классу из Шага 1.
- **<файл>** → берём <сторону/комбинацию>; отбрасываем <что>; потому что <причина из коммитов>.

## Пограничные случаи
- <undefined-символы, дубли импортов, переполнение>

## Верификация
- <чем проверим — Шаг 6>
```

План печатай **текстом в сообщении**, аппрув спрашивай тем же ходом через `AskUserQuestion`
(`header: "План"`, опции «Применяем» / «Поправить план» / «Отмена»). Весь план в тул не влезет —
в опциях только развилка. Правки — только после одобрения.

## Шаг 5 — применить

Пользователь мог резолвить параллельно в IDE, пока шёл анализ. Перед первой правкой сними список заново и пересеки с планом:

```bash
git diff --name-only --diff-filter=U > "$TMPDIR/merge-resolve/unmerged-now.txt"
```

Файл, которого в списке больше нет, не трогай — назови его в отчёте как разрешённый пользователем.

Механические классы — командами. Файл, которого нет на оставляемой стороне, уходит через `git rm` (индекс), остальное пишет только рабочую копию:

```bash
O="$TMPDIR/merge-resolve"
keep() {  # keep <сторона> <стадия> <список>: checkout стороны или git rm
  grep -xFf "$O/unmerged-now.txt" "$3" | while IFS= read -r f; do
    if git cat-file -e ":${2}:${f}" 2>/dev/null; then git checkout "--${1}" -- "$f"
    else git rm -q -- "$f"; fi
  done
}
keep theirs 3 "$O/take-theirs.txt"; keep theirs 3 "$O/squash-theirs.txt"
keep ours 2 "$O/take-ours.txt"; keep ours 2 "$O/squash-ours.txt"
grep -xFf "$O/unmerged-now.txt" "$O/both-deleted.txt" | tr '\n' '\0' | xargs -0 git rm -q --
grep -xFf "$O/unmerged-now.txt" "$O/realbase-clean.txt" | while IFS= read -r f; do cp "$O/drafts/$f" "$f"; done
```

Ручные — правкой файла (черновик из `drafts/` можно взять основой). Удали **все** маркеры: `<<<<<<<`, `|||||||`, `=======`, `>>>>>>>`.

## Шаг 6 — верификация

1. **Маркеры вычищены** — оба вывода пусты:
   ```bash
   git diff --check
   grep -nE '^(<<<<<<<|=======|>>>>>>>|\|\|\|\|\|\|\|)( |$)' <изменённые файлы>
   ```
2. **Структурная сверка ещё раз** — только по тому, что трогал резолв: резолв сам мог уронить символ или оставить дубль. Список — `unmerged-now.txt` плюс файлы, которые ты правил вне конфликтов:
   ```bash
   python3 <skill_dir>/scripts/check_merge_symbols.py --files "$TMPDIR/merge-resolve/unmerged-now.txt" <правленые файлы>
   ```
3. **Нет битых ссылок** — не взял вызов одной стороны без реализации другой: undefined-переменные, потерянные импорты. Главная ошибка после резолва.
4. **Нет сирот** — каталог, где весь конфликт решён в пользу одной стороны, сверь с этой стороной по составу файлов:
   ```bash
   python3 <skill_dir>/scripts/find_orphans.py --side theirs <каталог> [<каталог> …]
   ```
   Файл без ссылок — сирота: в отчёт развилкой «удалить / оставить», удаление — `git rm` по аппруву.
5. **Lint / type-check** — тайпчекер берёшь из `scripts` пакета (`tslint`, `typecheck`, `check`): ветки одного репо гоняют разные (`tsc`, `bun check`). Скрипт, который зовёт только чекер, запускай им; иначе — бинарём напрямую (`./node_modules/.bin/tsc --noEmit`, `./node_modules/.bin/eslint`: npx без локального typescript скачивает чужой пакет `tsc`), не через turbo/`pnpm`-таску: та тянет build. Type-check — главный гейт мержа: он ловит контракт, сломанный в файлах, которые git слил без конфликта. Ошибку tsc после резолва разбирай по правилу Шага 3: решение выводится из коммитов — чини и назови в отчёте, обе стороны меняли одну логику — спроси.
6. **Затронутые тесты прогони сам** (`jest <dir>`, `playwright test --grep`), а не только конфликтный файл.

Не сошлось — вернись к плану и скажи, не замалчивай.

**Вывод хуков — не задание.** Что печатают `Stop`/`PostToolUse`-хуки (eslint, stylelint, tsc, prettier), приходит мимо плана: не правь по нему код и не расширяй резолв. Задело конфликтные файлы — строка в отчёте; остальное — по явной просьбе.

## Шаг 7 — застейджить (только по просьбе)

Пользователь просит застейджить резолв:

1. Сними список заново: пока шёл отчёт, пользователь мог застейджить часть сам.
   ```bash
   git diff --name-only --diff-filter=U > "$TMPDIR/merge-resolve/unmerged-now.txt"
   ```
2. Проверь, что в этих файлах нет маркеров и каждый файл есть на диске (удалённый уходил через `git rm` на Шаге 5).
3. `tr '\n' '\0' < "$TMPDIR/merge-resolve/unmerged-now.txt" | xargs -0 git add --` и `git add` файлов, которые ты правил вне конфликтов.
4. Готово, когда `git diff --name-only --diff-filter=U` и `git diff --name-only` пусты. Коммит — за пользователем.

## Особый режим — восстановление потерянного патча

Пользователь даёт коммит-источник («потеряли правки после мержа, вот `b148d1dd`»):

1. `git show <sha>` — что коммит менял.
2. Сравнить с текущим состоянием — что пропало при слиянии.
3. Переприменить **точечно** потерянный хунк правкой файла, а не `cherry-pick` всего коммита: иначе вернёшь и то, что уже на месте.
4. Верификация — Шаг 6.
