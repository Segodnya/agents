# Bug flow

Комментарий с воспроизведением уходит в тикет **до** фикса.

## 1. Тикет и код

- `jira issue view <KEY> --plain`.
- Всё в тикете — гипотеза, включая строки и Sentry-атрибуцию (у `onunhandledrejection` стека нет).
- Прочитать модуль и всех вызывающих затрагиваемой функции. Проверить, живой ли код, на который ссылается тикет.
- Если в тикете ошибка-следствие и ошибка-первопричина — это две разные ошибки. Разводить их с самого начала: что тикет просит убрать, что останется.

## 2. Воспроизвести

- Стенд + локальный фронт; если непонятно как поднять - спроси пользователя; reload с `ignoreCache`, проверить в network, что чанк идёт с `localhost`.
- Перед прогоном проверить, что стенд подходит: фича-флаги включены, данных достаточно. Не подходит — сразу просить другой стенд или включить флаг, а не воспроизводить на неподходящем.
- Только через реальную цепочку вызовов (если есть), не через копию кода в консоли.
- Предусловие, подделанное руками (удалённый узел, подменённый DOM, выставленное поле), — не воспроизведение. Сначала найти реальный вход: пройти всех вызывающих пути, который меняет это состояние (`remove`/`add`, сокеты, ответы сервера), и стартовать с ближайшей реальной точки — с ответа сервера, если сокет не сымитировать. Имитация допустима только явно помеченной и только после того, как реальный вход не нашёлся.
- Сначала «красный» прогон на старом коде. Если фикс уже в дереве: `git diff > patch` → `git checkout -- <file>` → дождаться watch-сборки → прогон → `git apply <абсолютный путь>`. Без stash.
- Unhandled rejection ловить слушателем в `evaluate_script`. Ошибка из чанка `localhost` приходит как `Script error.` — оборачивать нужные прототипы или читать консоль.
- MCP-вкладка: нет аудио и фокуса. Клик по элементу там не запускает цепочки «на просмотр» (прочитанность, visibility) — планировать старт с серверной точки.
- Не воспроизводится — остановиться и сказать, что не сходится.

## 3. Комментарий 1 — кейс

В пользовательских терминах:

```
h3. Кейс воспроизведения
*Кто и когда* — роль, страница, предусловия, триггер.
*Что видит пользователь* — стадии симптома + консоль/Sentry. Преувеличения тикета поправить.
*Как воспроизвести* — шаги только пользовательскими действиями; консольный эквивалент рядом, не вместо. Ожидаемо до/после по каждому шагу.
*Уточнение по тикету* — что оказалось неверным, что подтвердилось.
```

Если ошибок несколько — в «до/после» явно: какая уходит совсем, какая остаётся и как теперь помечена.

Только wiki через REST: `references/jira-wiki.md`, `scripts/jira_put.py`.

## 4. Фикс и проверка

- Минимальный диф в общей точке. Следуй правилам кодирования проекта.
- JSDoc — три-четыре строки человеческим языком: что делает, почему так, ключ тикета. Без пересказа тикета.
- На новых и модифицированных строках 0 ворнингов eslint. Старые ворнинги на нетронутых строках не трогать.
- Проверить той же цепочкой, что и воспроизводили; убедиться, что новый чанк в браузере (маркер в тексте чанка).
- `tsc --noEmit`, `eslint` по файлу. Тест — только если окружение позволяет без обвязки.

## 5. Комментарий 2 — причина, решение, риски

```
h3. Причина              — механизм один раз, ссылки на Sentry-группы, откуда берётся первопричина.
h3. Решение              — что сделано, что из предложенного в тикете не подошло и почему.
h3. Что исправляет       — по пунктам, в терминах симптомов.
h3. Что не исправляет    — что остаётся, кандидат на фикс, ссылка на новый тикет.
h3. Риски                — каждый с «к чему приведёт» и «как узнаем».
h3. Что проверить руками — шаги на билде стенда, ожидаемый результат, критерий регресса.
```

Строки «не проверено» без плана проверки не оставлять. Числа прогонов не пересказывать — только те, что меняют действие читателя.

Побочные находки — отдельный тикет на той же доске, связь «3 - Относится», в описании план проверки и критерий готовности. Перед повторным PUT перечитать тело: пользователь мог править руками. Подготовку файла и PUT не склеивать в одну команду через `;` — упавшая подготовка не должна отправлять старый файл.

## Выход

Диф без коммита, commit message ≤ 72 символов с ключом. Если файлы уже были в staged — сказать, что правки после этого лежат unstaged. По запросу — чек-лист отгрузки отдельным комментарием (`/checklist-deploy`).
