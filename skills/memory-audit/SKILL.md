# memory-audit — память против кода

Каждая запись памяти — гипотеза. **Вердикт** получает только та, по которой выполнена команда и прочитан её вывод.

```
Шаг 0  ГРУНТ      проект → каталог памяти + репозиторий + источники правды
Шаг 1  ИНВЕНТАРЬ  memory.py inventory → таблица + механические дефекты
Шаг 2  СВЕРКА     каждая запись → вердикт + доказательство
Шаг 3  ГЕЙТ       сам перепроверяешь каждое удаление и каждое противоречие
Шаг 4  ОТЧЁТ      вердикты + противоречия → стоп, ждёшь, что применять
Шаг 5  ПРАВКИ     резервная копия → удаление, слияние, сокращение → индекс
Шаг 6  ПРИЁМКА    inventory без дефектов, цифры «было → стало»
```

`SKILL_DIR` — путь из строки `Base directory for this skill:`.

## Шаг 0 — Грунт

- **Каталог памяти**: `~/.claude/projects/<cwd, где "/" и "." заменены на "-">/memory`. Без аргумента берёшь проект текущего cwd; `--all` → `python3 "SKILL_DIR/scripts/memory.py" projects` и вопрос, какие проекты брать.
- **Репозиторий**: имя каталога памяти кодируется с потерями (`core_backend` и `core-backend` дают одно имя) — путь подтверждаешь через `ls`, при двух кандидатах спрашиваешь.
- **Источники правды**, с которыми сверяется запись: код репозитория, его `CLAUDE.md` / `AGENTS.md` / каталоги правил, глобальный `~/.claude/CLAUDE.md`, исходники скиллов (не копия в кэше плагина).
- Фиксируешь текущую ветку репозитория: она идёт в отчёт.

Готово, когда названы каталог памяти, путь репозитория, ветка и список источников правды.

## Шаг 1 — Инвентарь

```bash
python3 "SKILL_DIR/scripts/memory.py" inventory <каталог памяти>
```

Скрипт печатает тип, размер и `modified` каждой записи, затем дефекты: пустые `name`/`description`, ссылки `[[…]]` в никуда, расхождение индекса с файлами. Цель ссылки — slug из `name:`, не имя файла. Давность записи читаешь из `modified` во frontmatter: mtime файлов одинаков у всего каталога.

Затем читаешь записи и раскладываешь их по темам. Кандидаты в дубли выписываешь сразу: записи одной темы, записи про поведение скилла, записи, чья тема совпадает с блоком глобального `CLAUDE.md`.

## Шаг 2 — Сверка

До 20 записей сверяешь сам. Больше — группы по 10–20 записей на тему, каждой группе субагент `model: sonnet`, все одним сообщением. Субагенту в промпт: каталог памяти, путь репозитория, список файлов, дефекты этих файлов из вывода `inventory`, источники правды его группы, определения вердиктов и формат отчёта дословно из этого раздела, запрет на любые правки.

Из записи выписываются проверяемые утверждения — путь, символ, флаг, значение конфига, «сделано / отложено», «правило такое-то» — и каждое проверяется командой.

| Вердикт | Когда |
|---|---|
| **оставить** | верно, неочевидно, из кода не выводится, меняет поведение в будущих сессиях |
| **исправить** | ценно, но часть утверждений устарела — названо, какая |
| **слить** | пересекается с другой записью, или правило общее для всех проектов и его место в глобальном `CLAUDE.md` / скилле, или запись про другой проект |
| **удалить** | журнал влитой задачи, код исчез, то же самое уже сказано в правилах / скилле / комментарии в коде, противоречит текущему коду |

Правила сверки:

- Задача «влита» — это коммиты в основной ветке: `git log <master|main> --oneline --grep '<KEY>'`. Вывод `--all` показывает и невлитые ветки.
- Путь из записи отсутствует в рабочем дереве → ищешь его по веткам (`git log --all --oneline -- <path>`, затем `git grep <pattern> <branch> -- <path>`): спеки и планы живут в невлитых feature-ветках.
- Баг «исправлен» — это исчезнувший путь кода плюс влитый тикет. Одно без другого даёт вердикт «оставить» с пометкой.
- Утверждение, видимое только на стенде или в браузере, помечается «не проверено» и на вердикт не влияет.
- Из большой записи-журнала вытаскиваются долговечные факты («спасти»): они переживут удаление отдельной короткой записью.
- Пара записей, расходящихся об одном предмете, — **противоречие**: обе строки цитируются, код решает, какая права.

Формат строки отчёта: `запись | вердикт | причина ≤ 20 слов | команда → что показала`.

Готово, когда у каждой записи из инвентаря есть вердикт с доказательством.

## Шаг 3 — Гейт

Отчёт субагента — гипотеза. Сам, одной командой, перепроверяешь:

- каждое «удалить»: названный путь через `test -e`, названный символ через `rg`, влитость через `git log <основная ветка>`;
- каждое противоречие: какая из двух строк совпадает с кодом.

Вердикт, чьё доказательство не воспроизвелось, понижается до «оставить» и уходит в отчёт с пометкой.

## Шаг 4 — Отчёт и стоп

В чат, без файла:

1. итог одной строкой: сколько записей в каждом вердикте, сколько байт уйдёт;
2. противоречия — пара записей, что в коде;
3. списки по вердиктам с причиной в одну строку; у «слить» названа цель;
4. что не проверено и по какой ветке шла сверка.

Затем вопрос, какие области применять: память, глобальный `CLAUDE.md`, исходники скиллов, правила внутри репозитория. Применяешь только названные.

## Шаг 5 — Правки

Порядок фиксированный:

1. **Резервная копия**: `cp -Rp <memory> <memory>-backup-<YYYY-MM-DD>` рядом с каталогом памяти. Копия уже есть → стоп.
2. **Спасти**: факты из удаляемых журналов записываются в новую короткую запись до удаления; после — читаются из копии. Каждый факт сначала сверяется с кодом; неподтверждённый отбрасывается и называется в отчёте.
3. **Удалить**: `rm` с буквальными абсолютными путями.
4. **Слить**: выживает одна запись, вторая удаляется. Общее правило уходит одной строкой в свой блок глобального `CLAUDE.md`, в голосе и плотности соседних строк; запись про другой проект переезжает в его память.
5. **Сократить**: остаётся факт или правило, `**Why:**`, `**How to apply:**`. Уходят история инцидента, номера строк, хеши, имена тикетов без пользы для поиска. `description` обновляется под новое содержание.
6. **Индекс и ссылки**: `python3 "SKILL_DIR/scripts/memory.py" reindex <каталог памяти>`, затем правишь ссылки на удалённые записи — на реальный slug либо убираешь из предложения.

Больше 15 записей на сокращение → форки по тем же группам, что в шаге 2; индекс и ссылки пересобираешь сам после них.

## Шаг 6 — Приёмка

`inventory` печатает «дефектов нет» (допустима ссылка-задел на ещё не написанную запись — называешь её). В чат: записей и байт «было → стало», что ушло в `CLAUDE.md` и скиллы, путь резервной копии, отступления от плана, непроверенное, найденные по дороге расхождения в коде и правилах, которые в область правок не входили.

## Жёсткие ограничения

- Удаление и правки — только после ответа пользователя на шаге 4 и только после резервной копии.
- `git add` / `git commit` не выполняются нигде.
- Резервную копию удаляет пользователь.
