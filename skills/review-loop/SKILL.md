# review-loop — разобрать правки в бэклог и вычистить его до дна

Цикл сходится потому, что **область ревью сжимается**, а не потому, что ревьюер однажды промолчит. Раунд 0 разбирает замороженный диапазон в **бэклог**. Дальше каждый раунд применяет фиксы и ревьюит **только собственный патч** — дельту, которую сам и внёс. Патч всегда меньше того, что его породило, поэтому дельта тает, а бэклог убывает: каждый раунд его вычерпывает, ничто не наполняет заново.

```
Step 0  SCOPE      заморозить диапазон
Step 1  DISCOVER   раунд 0: полное ревью замороженного диапазона → бэклог
Step 2  RESOLVE    разобрать с тобой всё поведенческое — ДО фиксов
Step 3  ROUNDS     раунд N: применить фиксы → отревьюить свой патч → решить вопросы тут же
Step 4  REPORT     итог
```

**Чего этот цикл больше не делает.** Он не перепроверяет исходный диапазон каждый раунд и не ждёт «чистого» раунда. Свежий ревьюер на одном и том же диффе находит что-то всегда — это шум, а не сходимость, и раньше он гнал цикл до упора, накапливая очередь вопросов. Останов теперь наступает по построению: бэклог пуст, либо **ратчет** дошёл до дна.

## Границы, которые цикл не переходит

- **Поведение сохраняется.** Раунд сам применяет только фиксы, после которых код делает ровно то же: типы, дубли, сложность, мёртвый код, недостижимая ветка, стиль. Всё, что меняет наблюдаемое поведение, — не применяется без твоего ответа.
- **Баг в новом коде — вопрос, а не фикс.** Починка бага = изменение логики, значит сначала «баг ли это?» и предложение, потом Edit.
- **Вопросы разрешаются в том же раунде, где возникли.** Ни один не переезжает в следующий: раунд, работающий поверх неразрешённого вопроса, ревьюит код на посылке, которую ты можешь отвергнуть, и его находки стоят ровно ничего.

## Step 0 — Scope

Диапазон **замораживается на весь цикл**: список файлов и строк, посчитанный один раз здесь. Строки, которые допишут сами фиксы, в область ревью не входят — иначе цикл сам себя кормит работой.

Заморозка ограничивает **что ревьюим**, а не **что правим**. Фикс имеет право дотянуться куда угодно, если этого требует сама правка: завести токен в `theme.css`, доэкспортировать тип, добавить хелпер соседним файлом. Ревьюить эти файлы никто не начинает — они просто получают правку.

Диапазон берётся из аргументов запуска — они старше любого автовыбора:

| Аргумент | Диапазон |
|---|---|
| `staged` | `git diff --staged` |
| `branch` / `branch <base>` | `git diff $(git merge-base HEAD <base>)...HEAD` |
| `<sha>` | `git show <sha>` |
| `<любая git-ревизия или ревизия..ревизия>` | `git diff <как передано>` |
| нет аргумента | staged, если он непустой; иначе branch |

`<base>` не назван → определить: `git symbolic-ref --short refs/remotes/origin/HEAD` (срезать `origin/`), иначе первая существующая из `main`, `master`, `develop`.

Аргументы приходят на естественном языке — «ревью ветки от develop», «последний коммит», «то что в стейдже». Разобрать их в таблицу выше, не переспрашивая.

Команды звать **голыми, без `rtk run`**: `git`, `grep`, `rg`, `find` перечислены в `exclude_commands` rtk — хук их не переписывает, диффы и так приходят полными. А `rtk run` переразбирает аргументы через `sh -c` и портит всё, что несёт кавычки, скобки или `;`. Диапазон пуст → стоп, «нечего ревьюить». Выбранный диапазон объявить одной строкой и идти дальше.

Заодно найти **проверку**: скрипт тайпчека или тестов в `package.json` / `Makefile` (`typecheck`, `tsc --noEmit`, `test`). Нашлась — она станет страховкой в Step 3. Не нашлась — идём без неё, это не повод останавливаться. `build` не запускать никогда.

## Step 1 — Discover

Один субагент через Task, полный доступ к инструментам:

> Ты делаешь разведочный проход итеративного ревью. Диапазон: `<diff-команда>`.
>
> 1. Прочитай SKILL.md скилла **review-staged** (соседняя папка, `../review-staged/SKILL.md`, обычно доступна и как `~/.claude/skills/review-staged/SKILL.md`) и выполни его Steps 0–2, подставив `<diff-команда>` вместо `git diff --staged`. Дисциплина «докажи, потом сообщай» (`evidence` = реальный `file:line`, недоказанное молча выбрасывается) действует полностью. Design-пасс (Step 4) пропусти.
> 2. Бери все severity — P0, P1 **и P2**. Гейт evidence (Step 2 review-staged) распространи на P2 тоже: их теперь применяют, значит и доказывать их надо так же.
> 3. Ничего **не применяй**. Это разбор, а не починка.
> 4. **Допиши каждой находке исполнимый фикс** — `steps`, упорядоченный список правок, по одной на место: `{"file","was","now"}`. Одна правка в списке — обычная замена снипета. Три — рефакторинг: завести хелпер, переписать три места вызова. Правка вправе трогать файлы вне ревьюируемого диапазона, если фикс того требует (новый токен в `theme.css`, доэкспорт типа, новый хелпер) — заморозка ограничивает область ревью, не область правки. Не сворачивай находку до «нужен хелпер» — пиши код, который применят как есть.
> 5. Раздели находки на три корзины и верни только JSON:
>    - `safe` — поведение сохраняется и `steps` полностью выписаны;
>    - `ask` — фикс меняет наблюдаемое поведение, включая исправление бага, который породили эти правки. Для каждого — вопрос пользователю и конкретное предложение;
>    - `blocked` — поведение сохраняется, но применить нельзя: фикс требует шага, недоступного этому циклу (пересборка шаблонов, кодогенерация, миграция, `build`). Назови блокер прямо — это не «не смог», а «упирается вот во что».
>    Сомневаешься между `safe` и `ask` — это `ask`. Сомневаешься, выписываются ли `steps`, — выписывай; корзина `blocked` только для внешнего препятствия, не для сложной правки.
>
> `{"safe":[{"file","line","severity","issue","evidence","steps":[{"file","was","now"}]}],"ask":[{"file","line","severity","issue","evidence","question","proposal"}],"blocked":[{"file","line","severity","issue","evidence","blocker"}]}`
>
> Git-правила: никаких `git add`, `git commit`, `build`.

Полученные две корзины — **бэклог**. Он конечен и с этого момента только убывает.

**Порог разговора:** в `ask` больше восьми пунктов → цикл не запускать. Показать список и сказать прямо: эти правки требуют обсуждения, а не автоматической чистки. Восемь открытых поведенческих вопросов — это не бэклог, это проект.

## Step 2 — Resolve

Разобрать **весь** `ask` с тобой сразу, до единого фикса, через `AskUserQuestion` батчами по четыре: вопрос + предложение + `evidence`. Ответы раскладывают пункты в `safe` (одобрено — теперь это обычный фикс) или в отклонённые.

Порядок именно такой, потому что фиксы, наложенные до ответов, приходится переделывать после них.

Сюда же добавить многошаговые фиксы, если в Step 0 **не нашлось проверки**: рефакторинг на три-пять мест без тайпчека и тестов никто не подстрахует, так что решение брать риск — твоё. Одна строка на пункт, без разбора кода. Есть проверка — вопрос не задаётся, фикс идёт как обычный.

`blocked` не спрашивать — по ним решать нечего, они уедут в отчёт как есть.

## Step 3 — Rounds

Раунды идут, пока `safe` не пуст. Каждый — свежий субагент; вся его память о прошлом — переданный бэклог и реестр.

> Ты ведёшь раунд №`<n>`. Замороженная область ревью: `<файлы и строки из Step 0>`.
>
> 1. Применяй фиксы из списка ниже. У каждого — `steps`, упорядоченный список правок: иди по нему сверху вниз, каждую ровно по `was` → `now`, хирургически, без попутных чисток. Многошаговый фикс применяется целиком или не применяется вовсе: `was` любого шага не совпал с файлом — откати уже наложенные шаги этой находки и отметь её `stale`. Половина рефакторинга хуже, чем его отсутствие. Список: `<safe-бэклог>`
> 2. Отревьюй **только собственный патч** — `git diff` по файлам, которые ты сейчас правил, ограниченный твоими же строками. Исходный диапазон не перепроверяй: его уже разобрал раунд 0, и повторный проход даст шум, а не находки.
> 3. Новую находку принимай, только если она (а) внутри замороженной области, (б) проходит планку раунда: `<планка>`, (в) не совпадает ни с чем в реестре. Планка ниже — молча отбрасывай.
> 4. Верни JSON: `{"applied":[{"file","line","severity","issue","evidence","steps":[...]}],"new_safe":[...],"new_ask":[...],"blocked":[...],"stale":[...]}`.
>
> Git-правила: никаких `git add`, `git commit`, `build`.

После каждого раунда, в главном контексте:

1. **Проверка.** Нашлась в Step 0 — прогнать. Упала на том, что до раунда проходило, — патч раунда откатить и вынести пользователю как вопрос. Это единственная страховка от слепого пятна дельта-ревью: фикс в файле A ломает файл B, которого патч не касался.
2. **Ping-pong.** Отпечаток каждого применённого патча (нормализованный: без пробелов и комментариев) складывать в множество. Раунд выдал отпечаток, который уже там, или патч, ровно обратный прежнему, — это спор двух агентов, и следующий раунд его продолжит, а не разрешит. Немедленно остановиться и спросить тебя, показав обе версии с их `evidence`. Severity роли не играет: спор из-за P2 разрешается так же, как из-за P0.
3. **Вопросы раунда.** `new_ask` не пуст — разобрать прямо сейчас, тем же `AskUserQuestion`, до следующего раунда. Не копить.
4. **Ратчет.** Планка приёма новых находок поднимается каждый раунд и вниз не ходит:

   | Раунд | Планка |
   |---|---|
   | 1 | P0, P1, P2 |
   | 2–3 | P0, P1 |
   | 4 | только P0 |
   | 5 | ничего — цикл окончен |

   Ратчет — безусловный останов: он не спрашивает у модели, пора ли заканчивать, а просто перестаёт принимать её вывод. Отброшенное по планке идёт в отчёт как «найдено, но вне бюджета», молча не пропадает.

5. **Дальше:** `safe` пуст → к Step 4. Иначе новый раунд с обновлённой планкой.

Между раундами одна строка прогресса: `Раунд 2: применено 3, осталось в бэклоге 4, планка P0-P1`.

## Step 4 — Report

```markdown
# review-loop — <N> раундов, <причина остановки>
_Диапазон: <diff-команда>_

## Применено (<count>)
- `P1` **`file.ts:123`** — issue _(раунд 2)_. _Проверено:_ evidence.

## Решено с тобой (<count>)
- `P0` **`file.ts:45`** — вопрос → твой ответ → применено / отклонено.

## Осталось (<count>)
- `P2` **`file.ts:78`** — почему не тронуто. Ровно одна из причин: `блокер: <какой>` / `stale` / `вне бюджета ратчета` / `отклонено тобой`. Причины «сложно», «требует рефакторинга», «нужен хелпер» не существует — такое чинится.

## Итог
<2-3 предложения: что вычищено, остаточный риск, можно ли мержить.>
```

Причина остановки — одна из: `бэклог вычерпан`, `ратчет`, `противоречие`, `упала проверка`. Пустые секции опустить. Пустой бэклог после разведки → `review-loop — разведка не нашла подтверждённых проблем, <N> файлов.`

## Hard constraints

- Область ревью заморожена в Step 0. Строки, дописанные фиксами, в неё не входят.
- Раунды 1+ ревьюят только собственный патч. Исходный диапазон разбирается ровно один раз.
- Ни один вопрос не переезжает в следующий раунд.
- Применять только фиксы, сохраняющие наблюдаемое поведение; остальное — после ответа пользователя.
- Никогда не применять находку без `evidence` с реальным `file:line`.
- Никаких `git add` / `git commit` / `build` — стейджинг остаётся за пользователем.
