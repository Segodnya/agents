# tech-task — НТЗ для фронтенд-задач

## Зачем это нужно

НТЗ — это документ, который читает **аудитор**, у которого нет твоей истории расследования, чатов и dev-сессий. Его задачи:

- согласовать решение и тест-кейсы **до** написания кода;
- зафиксировать рассмотренные варианты и причину выбора;
- спланировать отгрузку, откат и наблюдение метрик.

Главный анти-паттерн, ради которого этот скилл существует — «это не ТЗ, а заметки после анализа». Признаки: плотный список `файл:строка`, отсутствие нарратива, нет use cases по шагам, нет альтернатив с обоснованием, нет плана отгрузки/отката, нет декомпозиции с часами.

## Когда применять

Применять:

- новая фича или новый контракт между сервисами;
- крупный рефакторинг / изменения сборки / инфры;
- баг с неочевидным root cause, где правка идёт в нескольких слоях;
- ресёрч-задача, разбитая на этапы (сбор логов → анализ → фикс).

Не применять для тривиальных правок (опечатки, маленькие багфиксы в одном файле, мелкие интерфейсные правки без логики).

## Workflow

1. **Собери вход.** Спроси у пользователя или вытяни из контекста:
   - ссылка на тикет;
   - ссылки на дизайны и ленги (если фича пользовательская);
   - ссылки на смежные ТЗ (бэк, мобилки) — даже если их пока нет, отметь это;
   - известные corner cases, обсуждения в чатах, прошлые инциденты, на которые опирается задача;
   - какой код уже исследован — какие файлы/методы пользователь смотрел.
2. **Выбери ветку по типу задачи.** Используй decision tree ниже и прочитай соответствующий файл в `references/`.
3. **Сформируй каркас.** Возьми `assets/template.md`, предзаполни каждую секцию по доступному контексту. Пустые места помечай явно как `[TODO: уточнить — что именно непонятно]`, чтобы пользователь видел gaps.
4. **Прогоняй чек-лист.** В конце пройдись по `references/checklist.md` — это последняя защита от «заметочного» стиля. Озвучь, что не закрыто.
5. **Собери открытые вопросы.** Все `[TODO]` подними в конец документа в раздел «Открытые вопросы» — это то, что пользователь должен обсудить со стейкхолдерами.

## Decision tree — выбор ветки

| Симптом задачи | Файл в `references/` |
|---|---|
| Чиним конкретный баг с воспроизводимым сценарием, есть тикет с шагами | `bug-fix.md` |
| Делаем новую возможность / новый контракт / новый UX | `new-feature.md` |
| Меняем кодобазу / сборку / инфру; без видимых пользователю изменений | `tech-refactor.md` |
| Сначала собираем логи / гипотезы / тестовые группы, фикс — потом | `investigation.md` |

Если задача попадает в несколько веток (типично: «сначала ресёрч, потом фикс») — оформляй её как `investigation.md` с одной из подзадач, ведущей к багфиксу.

## Анти-паттерны (главное правило: «не заметки»)

Когда заполняешь шаблон, активно отлавливай в собственном выводе:

- список «где сидят проблемы» как `file.ts:NNN — описание одной строкой» без объясняющего нарратива и без сцепления с use case;
- use cases в виде только таблицы (без шагового сценария «1. пользователь → 2. система → 3. …»);
- «альтернативы рассмотрены» одной фразой, без `pros / cons / итог`;
- технические термины (`apply_to_all`, `ma_ignored_ids`, …) без определения в Глоссарии до первого употребления;
- «отгружаемся через маринад» без явной шкалы и условия успеха («доля 422 = 0 за N часов на M аккаунтов»);
- «будем мониторить» без указания инструмента и конкретного дашборда;
- отсутствие декомпозиции с оценкой часов и суммарной оценкой.

При обнаружении любого из этих признаков — переписывай абзац, не оставляй «как есть».

## Стиль вывода

- Русский язык. Markdown.
- Заголовки секций как в `assets/template.md` — не переименовывай и не пропускай разделы (пустую секцию помечай `[TODO: …]` или явно `Не применимо, потому что …`).
- Списки и таблицы — окей; нумерованные сценарии — обязательны в Use cases.
- Технических деталей не больше, чем нужно аудитору, чтобы согласовать решение. Не превращай ТЗ в дневник правок.
- Никаких эмодзи.

## Принцип «объясняй почему»

Каждое решение в ТЗ должно быть выводимо из самого документа — без чатов, тикетов и истории. Если в выводе появляется фраза вида «выбрали X», она обязана продолжаться через «потому что …» с указанием причины (производительность, безопасность, обратная совместимость, ограничения браузера, и т.п.). Аналогично в «Альтернативные решения»: каждая отвергнутая опция — с явной причиной отказа.
