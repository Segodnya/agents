# Ветка: tech-refactor

Используй, когда задача — изменения кодобазы, сборки, инфраструктуры **без видимых пользователю изменений**: оптимизация бандла, переезд на новый target, изменения webpack/Vite, ESM-миграция, изменения CI. Эталон стиля: ТЗ «Изменить порядок загрузки чанков».

## Что важно подсветить именно для тех.рефакторинга

Для рефакторинга главные вопросы аудитора:

- **зачем именно сейчас** — есть ли измеримая боль (FCP / TTI / bundle size / время CI / падающие сборки);
- **что именно меняется** в сборке/инфре — какие плагины, какие entry, какие конфиги;
- **как мы измерим успех** — какие метрики до/после, какой эксперимент;
- **что может сломаться** — подводные камни сборки, конфликты, поведение в edge-средах.

## Структура с акцентами

### Постановка
- Сформулируй проблему через метрику: «сначала загружается app.js, и только после него начинают загружаться все остальные чанки соответствующей страницы».
- Если есть текущие значения метрик (FCP, TTI, размер бандла) — приведи их. Если нет — отметь «бенчмарк нужно снять до правок».

### Реализация → Варианты
- Для рефакторинга вариантов обычно несколько (см. в эталоне: «плагин для webpack» vs «генерирование json с assets entry»). Их обязательно перечислить с pros/cons/итог.
- Для каждого варианта добавь раздел «Подводные камни» — это специфика рефакторинга, и аудитор будет искать именно эту секцию.
- Если планируешь начать с одного варианта и переключиться на второй при провале — скажи это явно («Начать эксперименты следует с 1 варианта, так как этот вариант не потребует изменения структуры роутинга»).

### Описание выбранного варианта
- Опиши пошагово, что происходит при сборке, что — при первой загрузке страницы, что — при переходе между разделами.
- Если меняется поведение mapping'а (например, рантайм-контроллер загрузки чанков) — опиши его как отдельный модуль с методами, очисткой, и логом ошибок.

### Подводные камни / Corner cases
- Конфликты `.css` чанков при добавлении entry.
- `null.[hash].js` / `null.[hash].css` при `splitChunks.chunks = 'all'`.
- Поведение `getAllAsyncChunks()` в граничных случаях.
- Отсутствие нужных типов в webpack runtime.
Каждый камень — что делаем, если упрёмся.

### Обработка ошибок
- Куда и с какими тегами логируем ошибки сборки / загрузки чанков (Loggly с тегом типа `webpack-chunk-injector`, payload `{detail, type}`).
- Что показываем пользователю, если статика не загрузилась.

### План отгрузки и отката
- Тех.рефакторинги сборки — это **рискованные** правки, маринад обязателен.
- Этапы: стейдж с автотестами QA → 200 аккаунтов на N дней → 1000 аккаунтов на N дней → all.
- Для каждого этапа — условие перехода («нет обращений в саппорт», «нет роста ошибок в `webpack-chunk-injector`»).
- План отката: revert PR, понятно ли это безопасно.

### Метрики
- Это критичный раздел для рефакторинга. Назови конкретный дашборд (Datalens / Grafana).
- Опиши схему эксперимента: добавляем параметр `experiment_id: 'plugin'` в метрики, на основе него фильтруем тестовые аккаунты и сравниваем с контрольной группой.
- До маринада — создать дашборд с тестовой группой и контрольной.
- Ожидаемое движение метрик: FCP, TTI, размер бандла, время до интерактивности.

### Альтернативные решения
- Например, «оставить как есть и оптимизировать только один тяжёлый чанк» — отверг с причиной.

### Открытые вопросы
- Совместимость с уже отгруженным кэшем у пользователей.
- Как получать current url в шаблоне header (если зависим от бэка).
- Поддержка legacy-сборок.

### Декомпозиция
- Декомпозиция тех.рефакторинга обычно крупная по времени. Используй формат с часами по подзадачам и сравни оба варианта по часам (как в эталоне: «Вариант 1 — ~50 часов», «Вариант 2 — ~55 часов»).
- Учти: ресёрч, написание плагина/конфигов, тесты, аудит, отгрузка по этапам, дашборд.

## Запахи именно для этой ветки

- «Улучшить сборку» без конкретной метрики, которую улучшаем.
- Один вариант без сравнения с альтернативами.
- Нет раздела «Подводные камни» — для сборки это значит, что грабли ещё впереди.
- Нет схемы эксперимента с `experiment_id` — невозможно различить, помог ли рефакторинг.
- План отгрузки без маринада на узкой группе.
