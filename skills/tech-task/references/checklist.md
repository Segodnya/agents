# Чек-лист «не заметки, а ТЗ»

Прогони перед тем, как объявить документ готовым. На каждый пункт ответь явно: «ок» или «недозаполнено, потому что …».

## Структурная полнота

- [ ] Все разделы из `assets/template.md` присутствуют; пропущенные явно помечены «не применимо, потому что …».
- [ ] В Ресурсах указан тикет (или явно: «отдельного тикета нет»).
- [ ] Если задача user-facing — есть ссылки на дизайны и ленги (или явно «без UI», «без новых текстов»).
- [ ] Если есть зависимость от бэка/мобилок — есть ссылки на смежные ТЗ или отметка «бэк автономно дорабатывает по тому же тикету».

## Постановка

- [ ] Объяснено, **зачем сейчас**, а не только «что меняем».
- [ ] Если есть прошлые инциденты или внешние требования (compliance, прод-авария, продуктовая цель) — они упомянуты.

## Глоссарий

- [ ] Каждый новый или нетривиальный термин определён до первого употребления.
- [ ] Для терминов, где есть варианты реализации (кука vs LS vs APP.constant и т.п.), сказано, какой выбран и почему.

## Use cases / сценарии

- [ ] Есть как минимум один нумерованный пошаговый сценарий «1. пользователь → 2. система → 3. …».
- [ ] Покрыты ветки по предусловиям (с фильтром / без, авторизован / нет, SSO / не SSO, и т.п.).
- [ ] Corner cases выделены и закрыты — что делаем при гонках, отсутствии LS, разлогине из другой вкладки, старых клиентах и т.п.

## Техническая реализация

- [ ] Раздел читается как **нарратив**, а не как `file.ts:NNN — короткая фраза` подряд десять раз.
- [ ] Для каждого решения видно, какие варианты рассмотрены и почему выбран этот; либо явно сказано «единственный разумный вариант, потому что …».
- [ ] Файлы упомянуты с пояснением, что именно в них меняется и почему правка идёт сюда, а не в соседний слой.
- [ ] Если меняется payload/контракт — есть таблица «было → стало» или «намерение → ключи в payload».

## API контракты

- [ ] Если эндпоинты добавляются/меняются — описаны метод, тело, заголовки, response, ошибки.
- [ ] Каждая ошибка из списка имеет код, detail и условие, при котором её ждать.

## Кейсы тестирования

- [ ] Покрыты сценарии из Use cases.
- [ ] Покрыты corner cases.
- [ ] Для каждого кейса есть **ожидание**, проверяемое QA или скриптом.

## План отгрузки и отката

- [ ] Этапы маринада указаны явно (стейдж → 200 → 1000 → all) или есть осознанное обоснование, почему этапы другие.
- [ ] Для каждого этапа есть **условие перехода** на следующий и условие отката.
- [ ] План отката описан: что revert-им, что остаётся, безопасно ли остающееся.

## Метрики

- [ ] Указан конкретный инструмент: Sentry / Loggly / Datalens / Grafana / собственный дашборд.
- [ ] Указан период наблюдения и пороговая величина «успешно/неуспешно».
- [ ] Для рефакторов — есть метрика «до» (бенчмарк) или явный план её снять.

## Обработка ошибок

- [ ] Каждая новая ошибка имеет место в логах: сервис, теги, поля payload.
- [ ] Описаны ретраи / fallback'и, если применимо.

## Альтернативные решения

- [ ] Перечислены отвергнутые варианты, кроме явно очевидно плохих.
- [ ] У каждого отвергнутого варианта — причина отказа в одной фразе.

## Открытые вопросы

- [ ] Все `[TODO]` из остальных разделов собраны сюда.
- [ ] Для каждого вопроса понятно, кого спрашивать или к какому моменту нужен ответ.

## Декомпозиция

- [ ] Есть пронумерованный список подзадач в порядке выполнения.
- [ ] У каждой подзадачи — оценка часов; в конце — суммарная оценка.
- [ ] Учтены: проектирование, фронт, бэк, клиенты, тексты, переводы, окружение, аудиты, отгрузка, документация, дашборды.
- [ ] Каждая подзадача укладывается в 1-2 дня и имеет проверяемый результат (можно показать менеджеру).

## Главный фильтр «не заметки»

Перечитай документ глазами аудитора, который видит задачу впервые. Если ловишь себя на мысли «тут непонятно без чата в Slack» или «здесь логика расследования, а не описание решения» — переписывай абзац.
