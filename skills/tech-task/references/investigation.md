# Ветка: investigation

Используй, когда задача — сначала собрать данные, найти причину, потом уже фиксить. Эталон стиля: ТЗ «Улучшение работы сокетов». Контрпример: «делаем X» — это `new-feature.md` или `tech-refactor.md`.

## Что важно подсветить именно для ресёрч-задачи

Для investigation-задач главное — **этапы**, **условие выхода из каждого этапа**, **критерий «достаточно»**. Если ТЗ написано так, что не понятно, когда исследование считается завершённым, аудитор это не пропустит.

## Структура с акцентами

### Постановка
- Опиши симптом: «нестабильная работа сокетов» / «всплески ошибок X на Y% юзеров».
- Сформулируй цель: «выявить причины и снизить количество нелегитимных сбоев до минимума».
- Не пиши решение в Постановке — оно ещё не известно.

### Испытуемая группа
- Кого включаем в эксперимент: «1000 платных аккаунтов Kommo, выбранных по активности и использованию разных источников».
- Если группа подбирается по логам — описать критерий отбора.

### Выбор инструмента логирования
- Это специфика investigation-веток. Для каждого инструмента (Sentry, Loggly, собственный сервис):
  - плюсы (что даёт, какие трейсы, какие фильтры);
  - минусы (ограничения тарифа, отсутствие sourcemap, отсутствие API для resolve);
  - решение по каждому минусу: что делаем (доработать сборку, дождаться N попыток, добавить флаг `isResolved`).
- Заверши выводом: «инструмент X подходит, потому что …».

### Перспектива / стоимость
- Если выбор инструмента имеет финансовые последствия (Sentry Team vs Business, $114 vs $301) — упомяни.
- Если есть триал — отметь, как используем.

### Ожидаемое количество логов
- На основе пилотных отгрузок: «1027 логов sockuro в час, 1060 amojo, ~500 юзеров → ~2 лога/час/юзер → +3 после новых логов → итого ~5 логов/час/юзер».
- Это нужно, чтобы аудитор оценил, не утопим ли мы сервис.

### Этапы реализации
Это сердце investigation-ТЗ. Структурируй по нумерованным этапам с явным условием выхода:

- **Этап 1 — Добавляем логи.** Перечисли, какие именно (причины отключения сокета, причины неудачного подключения, причины переподключения).
- **Этап 2 — Анализируем логи.** Каждый параметр анализа отдельным буллетом (количество юзеров в группе, по которым собраны логи, общее количество, разделение по сигнатуре, легитимные/нелегитимные, по браузерам, по приоритету). В конце этапа — решение: чья сторона (Front / Back).
- **Этап 3 — Приоритизация и устранение.** Точечные фиксы vs глобальное решение. На этом этапе появляется отдельное ТЗ для глобального фикса (упомяни это, оцени в часах).
- **Этап 4 — Мониторинг после правок.** Условие успеха: «уменьшение количества нелегитимных кейсов до минимума».
- **Этап 5 — Открытие логов на всех / закрытие задачи.** Что считаем «успешно дошли до конца».

### Ожидаемый результат
- Опиши observable-критерий: «отсутствие большого количества ретраев реконнекта у пользователей», с порогом («иначе будем расследовать кейсы, когда количество ретраев > 5»).

### План отгрузки и отката
- Логи отгружаются раньше фикса. Опиши порядок: логи на узкую группу → собираем → анализируем → решаем фикс → отдельная отгрузка.
- Откат для логов — отдельно от отката для фикса.

### Альтернативные решения
- Например, «перейти на другой сервис логирования» — отверг с причиной («не факт, что там будет столько «плюшек», которые в Sentry работают из коробки»).

### Открытые вопросы
- Как делать resolve в Sentry без Business-плана.
- Кого спросить про распиловку sourcemap.
- Где брать список аккаунтов для маринада.

### Декомпозиция
- Декомпозиция в investigation **по этапам**, а не по подсистемам. Это отличие от других веток.
- Каждый этап декомпозируется на подзадачи с часами:
  - Добавление лога о причинах закрытия сокетов — 2ч;
  - Логи для определения этапов подключения: ТЗ — 8ч, реализация — 16ч;
  - Сбор логов — 48ч (это сами часы наблюдения, не разработки);
  - Анализ — 16ч;
  - Фиксы: точечные — 40ч; глобальное решение: ТЗ — 16ч, реализация — 40ч.
- В конце честно скажи: «всё очень примерно, всё зависит от масштаба проблем».

## Запахи именно для этой ветки

- «Соберём логи и посмотрим» без условия остановки.
- Нет испытуемой группы или нет критерия её отбора.
- Нет анализа стоимости инструмента, когда выбор имеет финансовые последствия.
- Этапы есть, но без условий выхода из каждого этапа — невозможно понять, когда исследование завершено.
- Декомпозиция по подсистемам, а не по этапам (характерно для багфиксов, не для ресёрча).
