# Ветка: new-feature

Используй, когда задача — создать новую возможность, новый контракт между сервисами, новый UX-флоу. Эталон стиля: ТЗ «Авторизация».

## Что важно подсветить именно для новой фичи

Новая фича — это про **сценарии пользователя** и **обоснование инженерных выборов**. Чем сложнее ветвление сценариев (авторизованный/анонимный/SSO/прямой переход), тем критичнее аккуратный Use cases-раздел. Чем больше вариантов реализации (Web Worker / setTimeout / rAF / SharedWorker), тем критичнее раздел Варианты с pros/cons/итог.

## Структура с акцентами

### Постановка
- Опиши, какую проблему пользователя или системы решает фича.
- Если фича снимает старую боль — упомяни эту боль (как в Авторизации: «гонки между сервисами на бэке», «протухание токенов», «пропадание access токена»).
- Закончи целевым предложением: «Поэтому, нам необходимо …».

### Ресурсы и затрагиваемые сервисы
- Перечисли все сервисы — фронт, ядро, промо-страницы, мобильные клиенты — каждый отдельной строкой.

### Глоссарий
- Этот раздел в фичах обычно большой и обязательный.
- Каждый термин: определение + место хранения/жизни + обоснование выбора («через куку, а не через APP.constant, потому что при переходе на CSR бэкенд должен отдавать голый скелетон»).
- Не упоминай термин в Use cases до того, как он определён в Глоссарии.

### Use cases / Сценарии
- Разбей по веткам предусловий. Типовая структура для авторизации/онбординга:
  - happy path («юзер авторизуется через promo»);
  - переход по прямой ссылке без токенов;
  - переход по прямой ссылке с токенами (и дальше веера: оба токена протухли, протухший access, свежий access);
  - SSO-аккаунты;
  - не-член аккаунта.
- Каждый сценарий — нумерованный список «1. юзер … 2. бэк … 3. фронт …», с указанием системы-актора на каждом шаге.
- Сценарии должны быть полными — если шаг продолжается в другом сценарии, скажи «Дальше — флоу обновления токенов на фронте» вместо обрыва на полпути.

### Техническая реализация

#### Варианты реализации
Это сердце ТЗ для фичи. Для каждого варианта (например: setTimeout, requestAnimationFrame, Web Worker, SharedWorker):

- идея — 1-2 предложения;
- плюсы — буллеты;
- минусы — буллеты;
- итог — «выбран», «отвергнут», «оставлен как fallback», и **почему**.

Если выбран один вариант и есть fallback'и — опиши и тот, и fallback'и, как в Авторизации с Web Worker + setTimeout fallback.

#### Описание выбранного варианта
- Файлы, методы, экспорты.
- Поведение в текстовой форме («после того, как таймер закончился, отправляем запрос за обновлением токена, и ставим флаг в LS …»).
- Где хранится state (LS / cookies / в памяти модуля), и что делаем, если основное хранилище недоступно (всегда есть fallback на cookies для cross-domain state, например).

#### Corner cases
- Пользователь удалил cookie / state из LS вручную.
- Сразу несколько вкладок пытаются обновить токен — кто побеждает.
- Браузер тушит таймер при неактивности вкладки.
- SSO-аккаунты с собственным флоу.
- Запросы в сервисы с кастомной авторизацией (заголовки `x-auth-token`, `authorization`).

### API контракты
Если фича добавляет/меняет эндпоинт — раздел обязателен:
- Эндпоинт, метод.
- Request body, request headers (Cookie, CSRF), Response headers (Set-Cookie с подробностями).
- Response body (с типами полей и форматом — Unix timestamp, ms, и т.п.).
- Возможные ошибки: невалидный refresh, невалидный CSRF, не-доверенный клиент. Каждая — с кодом, статусом и detail.

### Кейсы тестирования и оценка результативности
- Кейсы — по сценариям из Use cases + corner cases.
- Оценка результативности — какие логи добавляем на бэке/фронте, чтобы понять, что фича работает. Период наблюдения и тэги.

### План отгрузки и отката
- Этапы маринада с условиями перехода.
- Для фичи с новым контрактом — оговори, что делаем со старыми клиентами в переходный период (например, «mobile старых версий ловят 422 — это acceptance»).
- Откат: если зависим от бэк-контракта — что remains, безопасно ли.

### Альтернативные решения
- Что отвергли на верхнем уровне (например, «оставить обновление токенов на бэке и закрыть конкретные баги точечно — не решает проблему гонок»).

### Открытые вопросы
- Продуктовые тексты, UX-копирайт, неочевидные семантики, спорные смежные функции.

### Декомпозиция
- Проектирование и согласование (фронт + бэк + мобилки если задеваются).
- Фронт-задачи (по модулям, с акцентом: timer-компонент, interceptor, network-метод, обработка ошибок, fallback'и).
- Бэк-задачи.
- Мобильные клиенты — если задеваются, отдельным блоком.
- Тексты ошибок и подсказок, переводы.
- Аудиты по каждому слою.
- Отгрузка по этапам, дашборд для наблюдения.

## Запахи именно для этой ветки

- «Прокинуть параметр X» без описания, какое поведение этот параметр включает в каждой ветке Use cases.
- Один вариант реализации без объяснения, почему он единственный.
- Нет описания, что делаем, если основное хранилище state недоступно.
- API-контракт без раздела «возможные ошибки».
- Use cases только для happy path.
