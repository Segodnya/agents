# Ветка: bug-fix

Используй, когда задача — починить конкретный баг с воспроизводимым сценарием. Контрпример к этой ветке: «работа сокетов нестабильна» — это `investigation.md`.

## Что важно подсветить именно для багфикса

Багфикс легко скатывается в «список того, что я нашёл во время дебага». Чтобы ТЗ читалось как ТЗ, а не как журнал расследования, фокусируйся на четырёх вещах: **корень**, **mapping корень → правка**, **контракт payload/состояния**, **сценарии до и после**.

## Структура с акцентами

### Постановка
- Опиши воспроизводимый сценарий («Шаги: 1, 2, 3 → ожидание: X, факт: Y»).
- Сошлись на тикет с инцидентом, если он есть.
- Если баг привёл к проду/аварии — короткое упоминание импакта (количество затронутых аккаунтов, время до фикса страховкой, и т.п.).

### Текущая ситуация (или «Баги»)
- Если багов несколько и они логически связаны — нумеруй: «Баг #1 — Empty payload», «Баг #2 — Stale selection».
- Для каждого: симптом → корень («в `module/file.ts:NNN` accept делает override `X`, затирая `Y`») → почему это приводит к симптому.
- Если есть «гипотетический» баг, который удалось не воспроизвести, — отметь явно: «закрываем как страховку».

### Где сидят проблемы
- Сгруппируй по слоям/стекам (Backbone vs React, фронт vs бэк, leads vs contacts).
- Каждый файл — **одна-две строки контекста**, что в нём не так, не голый `path:line`. Если нужно несколько правок в одном файле — нумеруй по строкам.
- Заверши группировку фразой, связывающей правки в один корневой контракт («Все эти точки сходятся к тому, что payload может прийти без `apply_to_all`»).

### Техническая реализация
- Структурируй как «N пакетов правок одной отгрузкой» — это помогает аудитору видеть, что задача отгружается атомарно, а не по кускам.
- Каждая правка: место (file:method) → что меняется → почему именно здесь, а не выше/ниже по стеку.
- Если меняется payload — обязательно таблица «намерение → ключи в payload» (типа таблицы из ТЗ «Мультибедствия» с `apply_to_all / filter / ids / !ids`).

### Кейсы тестирования
- Таблица «сценарий → ожидание»; покрой каждый баг из списка + регрессии.
- Для каждого случая, где раньше был баг — отметь, какой код ошибки/поведение должно вернуться (например, «422 с detail empty_payload_without_apply_to_all»).
- Включи кейс «старые клиенты» (mobile, кэш) — что они увидят и почему это acceptance, а не регрессия.

### План отгрузки и отката
- Багфиксы часто отгружаются одной отгрузкой без фича-флага — это уместно, но скажи это явно, с обоснованием.
- План отката: что произойдёт, если revert-нуть фронт; что произойдёт с бэк-контрактом; безопасно ли это.

### Альтернативные решения
- Особенно важно для багфиксов: «почему мы не оставили legacy guards под фича-флагом», «почему не делаем auto-deselect», «почему не sentinel-фильтр ids: [-1]». Перечисление отвергнутых вариантов снимает 80% вопросов на аудите.

### Открытые вопросы
- Список аккаунтов для маринада, копирайт ошибок, спорные семантики (например, надо ли применить тот же контракт к смежной сущности).

### Декомпозиция
- Багфикс часто кажется маленьким, но не пропускай декомпозицию. Минимум: проектирование, реализация по пакетам, тесты, отгрузка, наблюдение метрик 422 / связанных ошибок.

## Запахи именно для этой ветки

- «Исправлен баг» в одну фразу без описания, в каком из узлов системы лежит корень.
- Перечисление правок без сцепления через единый контракт.
- Отсутствие таблицы контракта payload — если правка касается данных, отправляемых на бэк.
- Нет анализа, как себя поведут старые клиенты (мобильные приложения старых версий, открытые вкладки до отгрузки).
