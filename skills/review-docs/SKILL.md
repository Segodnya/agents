НЕ для ревью диффа — это `review-staged`, и не для написания ТЗ — это `tech-task`.

# review-docs — ревью документа против кода

Документ состоит из **утверждений** — о коде («`WabaTemplateConstructor` тянет три пропса из бродкастинга», «`SchedulerFeatureConditions.php:140`»), о продукте, о плане работ. Ревьюер подкрепляет вердикт **доказательством** — строками, скопированными дословно из реального файла. **Гейт** выкидывает всё, чью цитату не нашёл в файле; выжившие — **находки** `#1…#N`. То, на что код ответить не может, — **вопрос** `Q1…Qn`, а не находка.

```
Шаг 0  ГРУНТ       документ + семья документов + репозитории + срез кода + треды MR
Шаг 1  ПРОВЕРКА    шард-агенты по секциям документа → утверждения + доказательства
Шаг 2  ГЕЙТ        выкинуть без цитаты / цитата не грепается / вне периметра → находки #N
Шаг 3  ТРЕДЫ       сверить с обсуждением MR спеки → пометить снятое
Шаг 4  ПОЛНОТА     холистический проход: чего в документе нет как в документе
Шаг 5  ОТЧЁТ       находки + вопросы + «не проверено» → чат + временный .md
Шаг 6  ПРАВКИ      (по явной просьбе) внести согласованное в документ
```

Вызов: `review-docs <путь к .md> [--no-mr]`, позже `review-docs fix` / `fix 3 7`.

## Периметр

**Периметр = сам документ + его семья + репозитории, которые он называет.** Ревьюер читает внутри периметра, гейт выкидывает всё, процитированное снаружи.

Навигация по **имени**, от утверждения к одной вещи, от которой оно зависит: `goToDefinition` / `findReferences` / `hover` / `outgoingCalls` для ts/js/tsx, php, rust, go (deferred-тул: сначала `ToolSearch("select:LSP")`, позицию бери из `workspaceSymbol`, всегда с `query`); `grep`/`rg` через Bash по литералу — когда LSP не достаёт (twig, CSS, `.po`, нетипизированный Backbone). Тулов `Grep`/`Glob` в сессии нет. Глобы в zsh — в кавычках (`--include='*.ts'`).

**Проверяются утверждения документа, а не кодовая база.** Утверждение назвало символ → `findReferences` по нему, а не `rg` по дереву.

## Шаг 0 — Грунт

### 0.1 Документ и его семья

Путь к документу — из вызова. Не дан → `AskUserQuestion`, не угадывай.

**Документ вставлен текстом в чат** (PRD, кусок ТЗ из тикета) → `Write` его дословно в `/tmp/review-docs-input-<YYYYMMDD-HHmm>.md` и работай как с файлом: гейт грепает цитаты по файлу.

`ls` его папки: соседние `.md` (`TASK.md`, `RESEARCH.md`, `DESIGN.md`, `PLAN.md`, `SEQUENCE.md`, `README.md`, `plan.md`) плюс документы, на которые он ссылается: тикеты-сателлиты, смежные ТЗ бэка и мобилок, MR с уже отгруженной частью. Это **семья**. Прочитай её целиком в главном контексте — без неё шард не отличит противоречие от повтора.

Пользователь назвал несколько документов сразу — все они ревьюируются, семья та же.

### 0.2 Репозитории — обязательно

Выпиши из документа и семьи каждое упоминание кода: имена репозиториев, пути вида `app/src/...`, `file.ts:123`, имена символов, ссылки на MR. Сгруппируй по репозиториям и резолвни каждый в локальный путь: **cwd — первый кандидат** (скилл часто зовут из самого репозитория кода, а документ лежит в спеках рядом); дальше — ссылки на локальные копии из аудируемого файла; дальше — поиск по имени в `~/Desktop` рядом с текущим репозиторием.

Не нашёл локально хотя бы один → **стоп**, `AskUserQuestion`: где смотреть этот репозиторий / проверять без него — тогда все его утверждения уедут в «не проверено».

### 0.3 Срез кода — по умолчанию свежий master

Документ описывает работу поверх master — по master и проверяется. Случайная фича-ветка даёт ложные «опровергнуто»: часть утверждений в ней уже реализована.

```bash
git -C <repo> fetch origin --quiet
git -C <repo> symbolic-ref --short refs/remotes/origin/HEAD   # дефолтная ветка, fallback master
git -C <repo> branch --show-current; git -C <repo> log -1 --format='%h %cd'
git -C <repo> status --porcelain | head -5
git -C <repo> rev-list --count HEAD..origin/<default>          # на сколько отстаём
```

Три случая, все — в том же `AskUserQuestion`, что и 0.2, третьего стопа нет:

- **На дефолтной ветке** → это срез. Отстаёт от `origin/<default>` → скажи на сколько и предложи ревьюить по `origin/<default>`.
- **На другой ветке** → спроси: по ней или по master. **Checkout делает пользователь** — скилл не трогает рабочее дерево.
- **Пользователь назвал ветку сам** («работаем от `feature/TASK-1094`», «фетчни `build_2026_08_17_...`, это ещё в работе») → эта ветка и есть срез, без вопроса. Ветки нет локально → `git -C <repo> fetch origin <branch>`, читать через `origin/<branch>`.

Срез (репозиторий, ветка, хеш, дата, отставание, грязь) идёт в шапку отчёта и в промпт каждого шарда.

**Документ может описывать код, который ещё не влит.** Перед вердиктом «символа нет / файла нет» — `git -C <repo> log --all -S'<символ>' --oneline | head -5` и `git -C <repo> branch -a --list '*<фича>*'`. Нашлось в невлитой ветке → не опровержение, а `УТОЧНЕНИЕ`: «есть в ветке `X`, в срезе ревью нет». Не находится >3 утверждений подряд → останови проверку: ревьюится не тот срез.

### 0.4 Треды MR спеки

Спека ревьюится в MR — часть вопросов к автору там уже снята. SKILL_DIR — абсолютный путь из строки `Base directory for this skill:`, не cwd:

```bash
python3 "SKILL_DIR/../audit-reply/scripts/fetch_mr.py" --url "<MR_URL>" --all
```

`--all` обязателен: резолвленный тред — это и есть «уже обсудили». URL нет в вызове → `glab mr list --source-branch $(git -C <repo-спеки> branch --show-current)`, показать найденное и подтвердить. Ничего → `AskUserQuestion`: вставить URL / `--no-mr`. `--no-mr` — единственный обход, пропускает шаг 3 и пишется в шапке. Скрипт упал (auth, чужой хост) → напечатать подсказку `glab auth status --hostname <host>` и продолжить без тредов, сказав об этом в шапке.

### 0.5 Разбивка на секции

`wc -l` документа, оглавление по заголовкам (`grep -n '^#' <doc>`). Разбей на секции по 150–400 строк по границам заголовков — зона одного шарда, с точными диапазонами строк. Секции покрывают документ целиком, без перекрытий.

## Шаг 1 — Проверка

### 1.1 Маленький документ → без агентов

До 300 строк **и** один репозиторий → отработай все чартеры сама, в главном контексте. Шаги 2–5 идут в полном объёме, гейт включительно.

### 1.2 Шарды

Спавни **всех шард-агентов одним сообщением** (`general-purpose`, Read + Bash `grep`/`rg` + LSP). Каждый получает: свои диапазоны строк документа, список репозиториев с локальными путями, срез кода, общий пролог, чартеры 1–4 и форму ответа.

**Модель шарда по секциям — `model: "sonnet"`, отдельным параметром в каждом вызове `Agent`:** узкий диапазон строк, явный чартер, механическая работа «найди в коде цитату под утверждение». Шард по сверке документов между собой (cross-doc) модель не переопределяет — он судит семью документов целиком. Без параметра шард наследует opus: за окно 2026-08-16..23 так ушли **16 шардов из 16** ($165,34), из них $114,83 в одной сессии.

Шард стабильно возвращает пусто на секции, где утверждения заведомо есть → перезапусти эту секцию без `model`.

**Треды и прошлые отчёты в промпт шарда не попадают** — что уже снято, решается один раз, в шаге 3, по готовому списку находок.

**Общий пролог — дословно в каждый промпт:**

> - **Ты проверяешь документ против реального кода. НИЧЕГО НЕ ПРАВЬ** — ни код, ни документ. Только читай и отчитывайся.
> - **Работай только по своим диапазонам строк.** Не уходи в соседние разделы документа, не прочёсывай репозиторий в поисках «что ещё не так».
> - **Каждый вывод подкрепляй командой и её выводом** (`grep -n`, `rg`, `sed -n`, `wc -l`) либо `file:line`, который ты открыла. Прозу без доказательств не принимай от самой себя.
> - **Цитата обязательна и дословна.** `doc_quote` — строки из документа, `code_quote` — из реального файла (2–10 строк, не переформатированные, не восстановленные по памяти). Гейт грепает обе обратно.
> - **Срез кода задан.** Читай ровно ту ветку каждого репозитория, что названа выше. Никаких `checkout`, `pull`, `stash`.
> - **Кода нет ≠ утверждение ложно.** Перед вердиктом ОПРОВЕРГНУТО проверь невлитые ветки: `git -C <repo> log --all -S'<символ>' --oneline | head -5`. Нашлось — вердикт УТОЧНЕНИЕ с именем ветки.
> - **Опровергнуть можно только проверяемое кодом.** Продуктовое поведение, договорённость с бэком, намерение автора, «а надо ли так» → `question` с формулировкой вопроса, а не находка с вердиктом.
> - **Не пересказывай документ.** Совпало — одна строка в `checked_ok`.
> - **Не нашла, чем проверить** (нет репозитория, нужен доступ, нужен прод) → `unverified` с причиной, а не догадка.
> - [вставить секцию «Периметр» дословно]

Форма ответа — это и ничего больше:

```json
{
  "findings": [{
    "severity": "P0" | "P1" | "P2",
    "kind": "неточность" | "противоречие" | "слепое пятно" | "нереализуемо" | "состав пакета",
    "doc_ref": "DESIGN.md:118-124",
    "doc_quote": "дословные строки из документа",
    "claim": "одно предложение: что утверждает документ и почему это неверно",
    "verdict": "ОПРОВЕРГНУТО" | "УТОЧНЕНИЕ",
    "code_quote": "дословные строки из реального файла",
    "code_ref": "frontend/src/.../file.ts:340-352",
    "repo": "core_backend",
    "command": "grep -n 'useTemplatesForSelect' -r frontend/src --include='*.ts'",
    "fix": "точная формулировка правки в документ"
  }],
  "questions": [{
    "doc_ref": "DESIGN.md:200",
    "doc_quote": "дословные строки",
    "question": "что именно спросить у автора",
    "blocks": "какое решение нельзя принять, пока нет ответа"
  }],
  "unverified": [{ "doc_ref": "...", "why": "репозиторий amojo локально не найден" }],
  "checked_ok": "одной строкой: что проверено и совпало"
}
```

- **P0** — по документу нельзя писать код или можно написать не то: факт опровергнут, документы противоречат друг другу, решение упирается в реальное ограничение кода.
- **P1** — слепое пятно: состояние, ветка или ошибка, которую код умеет, а документ не описывает; неполный контракт; неучтённый потребитель.
- **P2** — неточность, не меняющая решение: протухший `file:line`, съехавшее имя символа, неверный счётчик, устаревшая ссылка.

### Чартер 1 — Факты о коде

Каждое конкретное утверждение своей зоны: существует ли файл, совпадает ли строка, так ли называется символ, столько ли пропсов/импортов/строк, то ли делает функция. Счётчики («во всех 45 папках суммарно 15 строк импортов») проверяются счётом, а не на глаз.

### Чартер 2 — Реализуемость и состав

Предложенное решение против того, что код позволяет: слои и алиасы, существующие потребители символа, который документ двигает или сужает, тип-контракты, реальная цена «просто переиспользуем X». «Поднимаем X в общий слой» → кто сегодня зовёт X и что он тянет за собой (`findReferences` + `outgoingCalls`). Ломает существующих потребителей — P0.

**Самодостаточность пакета**, если документ делится на тикеты:

- работа приписана не тому слою: «фронтовый тикет», который по коду закрывается бэком или парой твиговых правок;
- тест-кейс приёмки закрывается кодом **другого** тикета — пакет не отгружается в одиночку, порядок должен быть назван явно;
- оценка часов не бьётся с объёмом, который виден в коде;
- зависимость между тикетами есть в коде, но не проставлена в таблице.

### Чартер 3 — Слепые пятна

Кейс, который код умеет, а документ не называет. Ищи по коду своей зоны: ветки `switch`/`if` по статусу, которых в документе нет; коды ошибок и провалившиеся запросы; пустые и загрузочные состояния; поведение при выключенном фича-флаге; права и роли; удаление сущности, на которую ссылается другая; гонка двух источников правды; миграция существующих данных. Каждое слепое пятно цитирует **место в коде, которое этот кейс порождает**.

### Чартер 4 — Противоречия

Документ против себя (раздел 4 и раздел 7 описывают разное), против семьи (`PLAN.md` утверждает то, что `DESIGN.md` отрицает), против уже отгруженного кода или MR, на который документ ссылается. Цитируются **обе** стороны, вердикт говорит, какая верна по коду. Код не решает → `question`, а не находка.

## Шаг 2 — Гейт

Механический, в главном контексте, без суждений. Выкидывай по первой непройденной проверке, считай причину:

1. `doc_quote` непустая и грепается в документ: `grep -nF '<самая длинная различимая строка>' <doc>`. **Голый `grep`, никогда `rtk run grep`.** Нет совпадения → выкинуть (*цитата не в документе*). Совпало далеко от `doc_ref` → поправить ссылку, оставить.
2. `code_quote` непустая и грепается в названный файл — тем же способом. Нет → выкинуть (*цитата не в файле*). Для `kind: "слепое пятно"` цитируется место, порождающее кейс, — грепаться оно обязано так же.
3. `repo` и `code_ref` внутри объявленного набора репозиториев, `doc_ref` — внутри документа или семьи. Нет → выкинуть (*вне периметра*).
4. `questions`: нужны `doc_quote` (грепается) и непустой `blocks`. Вопрос, ни на что не влияющий, — выкинуть (*вопрос ни о чём*).

Дальше — бухгалтерия:

- **Дедуп** по `(doc_ref, claim)`, в том числе между шардами. Оставляй бóльшую severity, длиннее цитату, конкретнее `fix`.
- **Сортировка** P0 → P1 → P2, внутри — по порядку в документе.
- **Нумерация**: находки `#1…#N`, вопросы `Q1…Qn` — две независимые последовательности. Этими номерами пользователь отвечает («3 и 7 валидны») и по ним выбирает шаг 6.
- **Не проверено**: `unverified` со всех шардов, слитые в один список. В отчёте он есть всегда, даже пустой («не проверено: нет»).
- **Счёт отброшенного** = сумма причин выше. Ноль находок → всё равно отчёт со счётом и шаги 4–5.

## Шаг 3 — Треды

Пропускается при `--no-mr` или если шаг 0.4 упал. Только для находок и вопросов, по всему списку сразу.

Для каждой находки ищи тред, покрывающий её: тот же файл документа и та же область (±10 строк — строки уезжают), или то же по смыслу в прозе. Суди объяснение, а не подчиняйся ему: «так задумано» без причины не закрывает ничего.

- **Закрывает** → находка **остаётся в своём бакете**, сохраняет номер, получает `✅ снято тредом #<n>` с цитатой автора и строкой, почему принято. Вычитается из счёта в шапке, в шаге 6 **не применяется**.
- **Не закрывает** → остаётся находкой + строка: что ответил автор и почему это не покрывает случай.
- Вопрос `Q` с ответом в треде → в отчёт как «отвечено в треде», с ответом.

## Шаг 4 — Полнота (advisory)

Один проход по документу целиком — о том, чего гейт не видит:

1. **Решение выводимо из документа?** Каждое «выбрали X» продолжается через «потому что …», у отвергнутых вариантов названа причина отказа.
2. **Термины определены до первого употребления?** Технические имена (`apply_to_all`, `review_status`) без глоссария.
3. **План отгрузки, откат, метрики, декомпозиция** — есть, если документ претендует на ТЗ.

Для ТЗ прогони `skills/tech-task/references/checklist.md` — называй непройденные пункты, не переписывай чек-лист в отчёт.

**Advisory, никогда не находка** — отдельная секция `D1…D3`. Максимум три заметки, молчание валидно. Каждая заметка = что отсутствует + что конкретно дописать. Не можешь сказать, что дописать, — заметки нет.

## Шаг 5 — Отчёт

**Полный отчёт идёт в файл. В чат — действенная половина**: та же нумерация, дословно из отчёта, без тел P2.

````markdown
# Ревью документа — <N> находок (<M> снято тредами) · вопросов: <k> · `<doc>`
_Семья:_ <соседние .md или «нет»> · _Срез:_ core_backend `master@a1b2c3d 2026-08-20`, amojo `master@e4f5g6h` <«отстаёт на N коммитов» / «дерево грязное» / «по просьбе — ветка feature/X»>
_Треды:_ <T> (открытых <O>, резолвленных <R>) · _MR:_ !<iid>
_Отброшено <D> из <T> утверждений: <a> цитата не в документе, <b> цитата не в файле, <c> вне периметра._
_Не проверено:_ <список с причинами, или «нет»>

## P0 — Ломает реализацию (<count>)

### #1 · `DESIGN.md:118-124` · неточность — claim

> <doc_quote — дословно из документа>

```ts
// core_backend · frontend/src/.../file.ts:340
<code_quote>
```

_Правка:_ <fix> · _Проверено:_ `<command>`

### #2 · `PLAN.md:83` · противоречие — claim ✅ снято тредом #7

> @<автор>, тред #7: «<цитата>»

_Оценка:_ <почему объяснение закрывает находку>. В `fix` не идёт.

## P1 — Слепые пятна и неполнота (<count>)
Та же форма.

## P2 — Неточности (<count>)
- **#8 · `RESEARCH.md:412`** — claim. _Правка:_ <одна строка>. _Проверено:_ `<command>`.

## ❓ Вопросы к автору (<k>)
> Код на них не отвечает — нужен человек.

### Q1 · `DESIGN.md:200`
**Вопрос:** <что спросить>
**Блокирует:** <какое решение нельзя принять без ответа>
> <doc_quote>

## 💭 Полнота документа (advisory)
- **D1 · <чего нет>:** что дописать
````

- Шапка отражает реальность: `_Треды: недоступны (<причина>)_`, `_MR: не проверялся (--no-mr)_`.
- Строка отброшенного есть всегда; нулевые причины опускаются.
- Пустые бакеты опускаются. Ноль находок → `Ревью документа — расхождений с кодом не найдено` + шапка + счёт + вопросы + «не проверено».
- Язык подсказки в фенсе по файлу (`ts`, `tsx`, `php`, `css`).

**Сохрани отчёт.** Полный текст, дословно, через `Write` в `/tmp/review-docs-<слаг документа>-<YYYYMMDD-HHmm>.md`. Последние две строки сообщения в чат:

```
Отчёт: /tmp/review-docs-automation-with-templates-20260822-1420.md
pbcopy < /tmp/review-docs-automation-with-templates-20260822-1420.md
```

Есть неснятые P0/P1 → закончить строкой `Внести правки в документ? (review-docs fix, или fix 3 7)`. Ждать пользователя.

## Шаг 6 — Правки (по явной просьбе)

Только по явному запросу после отчёта: `review-docs fix`, `fix 3 7`, «поправь эти три», «внеси». Никогда в том же ходе, что и отчёт.

1. **Выбор:** названы номера → ровно эти находки. Без номеров → все неснятые P0/P1.
2. **Никогда** помеченное `✅ снято тредом` и **никогда** вопросы `Q` — на вопрос отвечает автор, а не правка.
3. `Edit` по документу: `doc_quote` → формулировка из `fix`. Цитата больше не совпадает (документ уехал) → пропустить и сказать, не угадывать.
4. **Хирургически**: ровно то, что описывает находка. Никакой попутной вычитки, переформатирования, «заодно причешу заголовки».
5. Перечислить, что изменено (`#N` → `файл:строка`) и что пропущено; тот же список дописать в файл отчёта как `## Применено`.
6. Не делать `git add` / `git commit` — стейджинг оставь пользователю.

## Жёсткие ограничения

- **Два стопа, оба в шаге 0** (репозитории + срез кода одним вопросом, MR). Между шагом 1 и отчётом вопросов в чат нет — они копятся в бакет `Q`.
- **Гейт — единственная дверь.** Каждая находка в отчёте прошла все проверки шага 2, включая ветку «без агентов». Перечитать документ — не проверка; цитата берётся из реального файла.
- **Код только читается, рабочее дерево не трогается.** Из git разрешён только `fetch` и чтение (`log`, `show`, `branch`, `status`); ветку переключает пользователь. Единственные записи за прогон — файл отчёта, копия вставленного текста в `/tmp` и (в шаге 6) сам документ. Находка «в коде на самом деле иначе» правит документ; поменять код — другая задача.
- **Бизнес-логику решает автор.** Сомнение про продуктовое поведение, договорённость со смежниками или намерение — это `Q` с формулировкой вопроса, а не находка с вердиктом.
- **«Не проверено» — часть результата.** Ненайденный репозиторий, невлитая ветка, кусок за доступом попадают в отчёт списком с причиной, а не растворяются.
- **Заметки шага 4 — единственный текст без гейта**, и они никогда не попадают в P0/P1/P2.
- Вывод хуков (линтеры, tsc) приходит мимо пайплайна и находкой не становится — максимум строка в `_Прочее:_`.
